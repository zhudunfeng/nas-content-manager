# S03.2 高水位与备份根身份接缝核对

2026-11-23。状态：研究建议，待主线冻结；没有实现、迁移、接口或测试通过声明。本文只补充 `persistent-backup-design.md` 的两个接缝，不修改既有研究、`info.md`、任务状态或正式 spec，也不扩大 S03.1。

## 1. 最小推荐

1. 沿用现有单次准入短事务和高水位字段，将正常业务拒绝建模为可提交的 Outcome。准入事务产生的410、备份业务 409/503 都必须在本次高水位事务提交成功后才能作为确定结果发送；不能把它们作为触发 rollback 的错误。
2. 不为根身份新增物理字段。保留 `store_id`、`root_bound`、非秘密 marker 和进程内根句柄/身份核验，明确跨重启只验证逻辑命名空间。将“任何根换实体都 blocked”收窄为进程内换根 blocked，以及跨重启缺失/错误 marker、不能安全核对的根 blocked；停服完整搬迁允许更换物理实体。
3. 根初始化、探测、对账和持久发布失败只使备份子系统不可用。默认关闭且根离线不阻媒体/账号服务启动；读状态与关闭策略不以取得备份根租约为前提。

## 2. 高水位：可提交的业务结果与致命错误分离

### 2.1 不变量与观察范围

- 沿用 `W=86400000ms`、`F=300000ms`、`T=UUIDv7.requestTime`、`expiresAt=T+W`。本次准入使用固定的实际 UTC 采样 `N`，读取已提交高水位 `H`，令 `E=max(H,N)`；客户端 T 绝不推进 H。所有算术和存储范围先校验。
- 只有时钟事务成功提交的采样才是系统确认的备份时钟观察。已发布的终态过期结论依赖该已提交 H；被取消、鉴权失败或确认回滚的临时采样不构成已提交观察。
- 事务内部可以暂存 H 的更新和待返回的 Outcome，但提交前都不能称为持久事实。成功提交满足 `Hnew=max(Hold,N)`，H 不降低；后续准入、时钟维护和裁剪使用同一规则，不能各自保存回退后的墙钟。
- GET 保持只读，不推进 H。会话过期仍按认证所用的实际 UTC 判断，不使用备份 E 延长或缩短会话；紧邻提交的认证采样不改写本次已经固定的备份时钟决策点。

本节只约束进入幂等准入/时钟维护事务的结果，不要求下载、取消、策略关闭等其它操作的所有409/503写 H；这些入口沿用各自契约。

### 2.2 精确顺序

| 顺序 | 动作 | 提交边界 |
| --- | --- | --- |
| 1 | 做严格 DTO、UUIDv7、同源和初始鉴权检查；检查请求 ctx 与模块是否已封准入。根探测/初始化等慢 I/O 只在事务外进行，取得本模块受保护的 readiness 事实。 | 输入/初始鉴权不通过时不进入备份时钟事务；根不可用不是绕过高水位的提前业务返回。 |
| 2 | 取得短准入锁，开启事务，通过同一事务 reader 再验会话/账号修订；检查 ctx。 | 失效则确认 rollback 后按原认证规则返回；不能把 `account_changed` 与正常备份业务 409 混为一类。 |
| 3 | 采 N、读单例 H，固定 E；仅当 N>H 时推进 H。缺单例、SQL 错误等属于存储失败。 | 条件 UPDATE 的零行不一定是错误，可能只是 N<=H；须先确认单例存在。 |
| 4 | 先查账本以及仍保留的对应 run。已知非终态即使过窗也返回同一 run；已知终态按 E 决定重放或410。 | 不因 busy、根离线、回拨或账本满而覆盖已知事实，不续期、不新建。 |
| 5 | 未知键先按 `T<=E-W` 判410、`T>E+F` 判409；余下才检查严重回拨、活动占位、策略/readiness 修订及容量。 | 各正常拒绝仅形成 Outcome，继续到最终提交步骤；根不可用、busy、容量满仍可推进 H。 |
| 6 | 对可接受的新键，先有界查询可回收的过窗终态键，计算回收后的容量；所有准入条件通过后才执行这些删除并同事务插入 queued run 和 request key。 | 拒绝分支不裁剪账本或 run 历史，只提交必要 H 更新；接受分支的回收与插入原子提交。不能删除有效键、非终态键或文件所有权记录。 |
| 7 | 紧邻提交再次检查 ctx、模块关闭状态、敏感会话与账号修订。 | 失败则整个事务 rollback；成功形成的认证拒绝/取消取代尚未提交的备份 Outcome。 |
| 8 | Commit，确认成功后释放锁并发送已选 Outcome；新接受 run 在提交之后唤醒 executor。 | Commit 错误或结果未知时，不发送预选410/409/503/202，不声称肯定未接纳；返回受控存储错误并要求沿原 requestId 核对。 |

实现应在类型层面区分“可提交的业务 Outcome”和“必须中止的存储/认证/取消错误”。资源兜底用的 deferred rollback 可以保留，但不得以“Outcome 的 HTTP 不是2xx”作为退出事务的条件。一次准入只固定一个 E；不得在同事务不同分支重采时间，形成裁剪与重放边界不一致。

拒绝路径不裁剪是本片的最小选择，不新增第二笔独立时钟事务或 savepoint。容量检查可在最多2048条账本内查询到期可回收集合，再决定是否接受；若仍无槽位，503只保留 H 的推进。原有显式维护/调度裁剪仍可执行有界清理，但须先在它自己的短事务持久推进 H，再按同一 E 判断到期；不要因本片而增加无界清理任务。

所有 readiness 预检只能影响候选 Outcome，事务内仍须检查对应管理器状态/修订是否未改变。大 I/O 不进入事务或 `backupManager.mu`。必要的显式根初始化可能单独创建控制用 marker 并 CAS `root_bound`；它不代表接受了 run。不能把“未创建执行记录/备份候选”宣传为“整个请求无磁盘或数据库写入”。

### 2.3 拒绝、取消与存储未知矩阵

| 情况 | H / run 处理 | 可对外陈述 |
| --- | --- | --- |
| 正常备份410、busy/time-ahead/policy-changed 409、clock/storage/readiness/capacity 503 | 保持可提交 Outcome；成功提交 H；拒绝不插入 run/key、不分配 fileId、不推进计划 cursor，不生成执行产物。N<=H时可以没有实际 H UPDATE。 | 该业务拒绝已确定；“没有接受新 run”成立，“数据库零写”不成立。 |
| 会话/账号快照在事务内失效，或提交前 ctx/关闭检查失败，且 rollback 确认成功 | 回滚 H 和全部暂存业务修改；认证/取消检查使用原有规则。 | 仅返回认证/账号变化/取消结果；不把先前算出的410等当作已提交观察发布。客户端已断开时不承诺 HTTP 响应。 |
| SQL 失败且 rollback 确认成功 | 不提交本次 H/run；已有已提交 H 不受影响。 | 受控存储失败；不把尚未提交的业务 Outcome 冒充成功结果。 |
| Commit 报错、提交期间取消，或 rollback/连接状态使结果不能确认 | 保留“可能提交”的分类；不得靠 `context.Canceled`、超时或错误文本推断零写。 | 受控存储错误/未知结果；原 requestId 核对，不自动换键重发，不返回“肯定未接纳”。 |
| Commit 已成功，但响应丢失或 ctx 随后取消 | H/run 已提交；不得补偿删除。 | 原键重放同 run 或终态摘要；HTTP 断开不撤销已接受任务。 |

`backup_policy_changed` 等备份域的正常409与凭据修订变化的 `account_changed` 不同：前者提交 H 后返回，后者必须中止敏感事务。503 `backup_storage_unavailable` 指根/readiness 已知不可用的正常业务状态；数据库不可写、事务失败不是可提交的503，应走受控存储错误路径。

计划 tick 没有 Web 会话，但仍受应用生命周期 ctx、模块准入和策略修订约束。参与时钟判定/裁剪的 tick 使用同一 H 规则；正常 busy/根离线不推进 cursor、不堆积失败 run。停机前取消且 rollback 确认成功的 tick 不是已提交时钟观察。

### 2.4 必须防住的反例

设旧 `H=1000000`，某终态键到期值 `X=1000050`，本次实际 `N=1000100`。如果计算410后把它当错误 rollback，H仍为1000000；下次时钟回到1000000，就可能再次返回窗口内200，形成已宣告过期的结果复活。

正确顺序是在发送410前提交 `H=1000100`。之后任意回拨均有 `E>=H>=X`，因此该键一直410；即使该过窗终态键以后被裁剪，未知键的 `T+W<=E` 仍拒绝重新执行。busy、time-ahead、容量拒绝也必须保留同样的真实观察。已知非终态过窗仍返回同一 run 是既定查询规则，不是新执行或续期。

如果步骤7发现会话失效/ctx取消并成功 rollback，系统不能同时对外发布权威410；只返回认证/取消结果，故没有“已发布410后来又200”的承诺冲突。事务提交未知则按未知处理，不能伪装为确认回滚。H只有一个整数、账本有固定上限，新增的是受控写频率成本，不是无限历史；N<=H不做无意义更新。

## 3. 备份根：分清三种身份与搬迁边界

### 3.1 当前字段实际能证明什么

| 层次 | 可用凭据 | 能保证 | 不能保证 |
| --- | --- | --- | --- |
| 单进程持有期间的物理身份 | 根句柄、该句柄对应的 OS 身份、当前路径解析身份、marker、独占根租约 | 在受支持平台上，关键 I/O 前后核验操作仍指向本次打开的根；发现运行期换根、链接或标记异常即阻断本模块后续写入。 | 不抵御同权限管理员持续篡改；OS 身份与持久性仍受平台/文件系统实测边界约束。 |
| 跨正常重启的逻辑命名空间 | DB 的 `store_id/root_bound` 与固定 marker 的 magic/formatVersion/storeId | 识别该配置根声明属于本 DB 的备份命名空间；缺失或不匹配时拒绝悄悄接管。 | 非秘密 marker 可复制，不能证明仍是上次物理盘、卷或目录，不能分辨完整迁移与完整克隆。 |
| 停服完整搬迁后的接续 | 同 DB 谱系/同 storeId、完整迁移材料、重新取得根租约并对账 | 允许跨卷/目录物理变化后重新建立本次进程身份；逐项核对自己登记的文件和意图。 | 不证明所有未登记材料也已复制，不证明原副本已销毁，不提供跨两个独立克隆根的全局互斥。 |

现有 `root_bound=1` 不包含上次物理身份，不能推出“跨重启物理实体变化必能检测”。新增同样可复制的 `root_nonce`、随机 marker ID 或把路径字符串存库也不会补上这一证明。最小推荐是不增字段、修正承诺，不把逻辑标记包装成不可复制的物理身份。

### 3.2 建议冻结的根契约用语

- **进程内**：取得根租约并打开根后，记录本次根句柄与身份。关键 I/O 前后核验路径/句柄/marker；变化即备份模块 blocked，不允许仅因新目录带有相同 marker 而热切换继续写。
- **跨重启**：已绑定 DB 遇到缺 marker、格式/版本不支持、storeId 不同、无法安全解析/加锁/隔离的根时 blocked/unavailable。真实空目录或拔盘后的无 marker 空挂载不得重新初始化，不自动生成新 storeId、重写 marker 或寻找/接管另一根。
- **内容与身份分开**：相同 marker 只通过命名空间检查，不把已有产物直接视为有效；仍按现有有界对账逐项核验 DB 意图、owner、成员、manifest、长度/hash/schema。缺失/损坏按其真实状态处理，根整体不可用时不把全部文件批量改 missing。已有合法 marker 且尚无备份文件可以是“绑定后尚未首备份”，不能仅因没有 `b-*` 目录断言物理换根。
- **合法搬迁**：先正常停止所有持有该 DB/根的进程，完整搬迁原专属根及 marker，保持与原 DB 记录相配，修改宿主 `NAS_BACKUP_DIR`；启动后重做路径隔离、根租约、标记及有界对账，成功后才开放新准入。搬迁可以改变物理实体，不自动搬文件、不在线热切换、不清理旧根。
- 复制可以作为停服搬迁手段，但管理员必须选定单一权威副本，不同时写入两个克隆命名空间。根锁只互斥同一实体，无法阻止两份独立复制根各自成功加锁；不能以本方案声称已检测或禁止所有离线克隆。
- 首次 `root_bound=0` 仍只接管新/空专属目录，或相同 storeId 的已知 marker；排他根租约下写 marker、确认必要落盘后 CAS 绑定。崩溃留下匹配 marker 可补绑定，不能因 root_bound=0 而覆盖未知非空目录。

若产品坚持“跨重启不同物理实体一律拒绝”，则至少需要持久的平台物理身份、支持矩阵和显式离线搬迁授权/重绑定协议，同时重定义跨卷搬迁、还原和克隆行为。单独加文件ID/卷ID仍有重用、平台差异与复制边界；不能承诺不可伪造。本片不新增该协议、CLI或维护入口，也不冻结这一更强产品选项。

## 4. 默认关闭与根离线的生命周期

| 状态/动作 | 备份子系统行为 | 主服务行为 |
| --- | --- | --- |
| 首次默认 disabled 且 root_bound=0 | 不要求启动时创建根/marker或持有根锁。可报告 uninitialized/unavailable；首次显式手动备份或启用才尝试受控准备。 | 媒体、账号等正常就绪，不因备用根暂不可访问而 fatal。 |
| root_bound=1，但根缺失/锁被占用/挂载离线/权限不足 | 报告根 unavailable/mismatch；不新建空根替代，不生成持久目标、不轮转、不批量标记所有产物 missing。状态查询继续可用。 | 备份对账不阻主服务就绪，错误留在备份状态与安全中文日志中。 |
| enabled=true 时根临时离线 | 保留用户 enabled=true 意图，暂停新准入；无新 run、无 cursor 推进，不按遗漏周期制造失败记录。根恢复并安全对账后按既定 latestDue 规则处理。 | 仍可正常使用其它功能；不以静默关闭策略掩盖故障。 |
| GET 状态、PUT enabled=false | 不以根租约/探测成功为条件；关闭仍需正常鉴权、策略 CAS 和可用 DB，不删已有备份，已接纳执行按既有取消规则处理。 | 管理员能查看故障并停止未来计划。 |
| 兼容 GET /api/backup | 只受 S03.1 自己的源库、预算、快照租约及原接口条件约束。 | 不额外依赖持久备份根，保留时钟故障/根离线时手动导出的退路。 |
| 根重新可访问 | 在下一次显式操作或既有单 executor 的有界检查中重新 probe/取得租约并对账；完成前不开新持久准入。 | 不增加阻塞全站启动的无界等待或第二套后台循环。 |

静态配置语法/路径隔离不合法与临时 I/O 不可用应在错误分类中区分。本片不重定义全应用配置失败策略，但默认关闭且根暂时离线不得变成整个媒体服务的启动失败。若运行期根身份改变，必须停止/收尾该根上的相关 I/O 后重新建立受控状态，不能用一轮成功 probe 自动抹掉 mismatch 并热接另一实体。

## 5. 后续冻结与验收输入

本轮未运行产品 lint、类型检查或业务测试；仅研究文档，无新增测试源。以下是 S03.2 实施前须纳入现有验证矩阵的待验条件，不能记为 passed：

1. 终态键到期、time-ahead、busy、root unavailable、dedupe full、ownership full 各拒绝一次，分别核对已提交 H；重启后注入回拨，已宣告过期的键不能回200/202或新建 run。
2. 在最终会话复核/ctx检查前后加确定性 barrier：确认 rollback 时 H/run不变且不发候选410；确认 Commit 后响应丢失时原键仍回同 run。Commit/rollback 结果未知须留未知证据，不算零写。
3. 拒绝路径只推进 H，账本/run/cursor/file意图不变；仅回收过窗终态键，不能为了腾位驱逐有效键；接受分支回收与插入同事务。N<=H与条件 UPDATE 零行不误判存储失败。
4. 进程内替换根，即使复制 marker 也阻断；重启遇无 marker 空挂载、错误 storeId、锁占用、只读根均不初始化或清理未知文件。合法未首备份根不被误判为换盘。
5. 停服完整搬迁到另一物理实体，通过正常核验和对账后可接续；明确这不能证明拒绝离线克隆。只复制 marker/部分文件不得被宣传为完整迁移或完整备份验证通过。
6. 默认 disabled/已绑定根离线/enabled根离线分别验证主媒体服务可用、GET状态可用、关闭策略可用、无 cursor推进和失败run堆积；兼容临时快照不依赖持久根。恢复挂载后验证有界对账再开放。

主线若接受最小推荐，只需在正式冻结时同步高水位事务顺序、业务/致命结果类型、根身份承诺与生命周期文字；无需因本片引入新物理字段、签发秘密或离线维护命令。是否接受 marker 的跨重启逻辑身份边界，以及严重时钟误跳的既有保守运维限制，仍须在 S03.2 冻结记录中明示。
