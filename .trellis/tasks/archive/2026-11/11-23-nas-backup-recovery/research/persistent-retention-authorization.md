# S03.2 持久轮转授权的最小契约

2026-11-23。状态：独立研究建议，待主线冻结；没有实现、迁移或产品验证通过声明。本文只核对 `persistent-backup-design.md` 第3、7、8节的轮转授权缺口，不读取并发 S03.1 产品代码，不修改既有研究、正式 spec、`info.md` 或任务状态。

## 1. 结论与必须明确的取舍

`last_good_file_id` 是恢复点候选指针，不是待执行删除凭证。它既不会在轮转结束时消失，也不能说明哪一版保留参数曾获授权；不能在重启、下载租约释放或策略编辑后凭它重新开始删除。

推荐保留五表，仅为 `backup_store` 增加三个可空字段，持久保存**一份**待续授权。每次新成功同时记录授权来源和当时最新保留阈值；续跑时只在该授权范围内采用当前策略。原“轮转直接使用当前最新策略”必须明确收窄为：

> 每次新删除认领使用“本次成功授权的阈值”与“当前最新已提交阈值”中较宽的组合。编辑变严不能扩大旧授权，下一次成功才授权更严规则；编辑放宽可以减少尚未认领的删除。已经提交为 deleting 的确切删除意图继续受控收尾。

这不是同时保留原文两种相反承诺：如果坚持旧授权续跑时立即完整应用更严的新策略，就必须放弃“只改保留参数后等下一成功点才删”的契约。本片推荐上述较保守语义，不引入通用队列、独立轮转 run、API 或维护命令。

## 2. 持久字段与不变量

### 2.1 仅增加三个字段

| 表/字段 | 建议类型与约束 | 中文含义 |
| --- | --- | --- |
| backup_store.retention_authorizer_file_id | TEXT NULL；非空时为规范32位小写hex | 本次仍未结束的轮转授权，来源于哪一个已经有效发布并登记完成的文件。该值同时是 CAS token，不是待删文件。 |
| backup_store.retention_authorized_keep_count | INTEGER NULL；非空时1..30 | 该成功点允许应用的保留数量阈值。值越小，删除权限越强。 |
| backup_store.retention_authorized_max_bytes | INTEGER NULL；非空时67108864..1099511627776 | 该成功点允许应用的自有逻辑字节阈值。值越小，删除权限越强。 |

三者必须全 NULL 或全非 NULL，由同一 CHECK 约束；迁移默认全 NULL。全 NULL表示没有待续授权，不能从 last-good、历史 completed、当前超额或最后成功摘要反推授权。全非 NULL表示待续，因下载、I/O、guard或根故障而暂停仍保留这一份记录。

不另外增加 pending 布尔值、授权自增序号或持久策略 revision：三字段已分别表达活跃性/唯一成功来源和两种删除权限边界。当前 `backup_policy.revision` 仍用于每次短事务的并发核验，但仅存一个旧 revision 无法恢复已被编辑覆盖的旧 keep/max，不能代替这两个阈值。无需新增第六张表。

### 2.2 必须成立的关系

- 授权来源必须属于本 store，对应实际完成的文件/运行；`run_seq` 是删除范围的成功点上界。只处理不晚于该来源 `run_seq` 的自有 completed 文件，不能把将来另一个候选纳入旧授权。
- 活跃授权引用的来源文件行及其运行事实不得被历史压缩/ownership清理移除；仍无级联删除。结束授权后回到原有有界裁剪规则。来源后来 missing/unverified 不等于授权从未存在，但不得将其当有效 guard。
- 一次最多一个 `deleting` 文件，建议在 `backup_files` 增加 `state='deleting'` 的单行部分唯一索引；沿用现有 state 和所有权元数据，不增加删除任务表。授权未结束或既有 deleting 未收尾前，不开始下一份持久目标生成。
- `last_good_file_id` 与授权字段相互独立：前者可因有效性复核改指另一个 guard；后者只在本次成功发放与结束时整体改变，不能随 guard 改指而重开、扩权或续期。
- 时间不决定授权有效期，不因重启/墙钟回拨自动失效；授权体积固定，至多一份。重试由既有单 executor 的有界唤醒承担，不增加无限重试行、每文件工作流或第二个执行器。

## 3. 发放、认领、收尾与结束的原子点

### 3.1 只有新的成功状态转移才能发放

完成必要的平台发布与校验后，原有短事务同时：

1. CAS 原 run/文件意图从 running/pending 变为 completed/retained；检查确为这一次新的状态转移。
2. 更新去重摘要、最后成功与 last-good。
3. 读取此事务中最新已提交策略的 keep/max，将来源 fileId 与两阈值写入三个授权字段。

事务失败或结果未知时不另发“轮转可以开始”的内存信号；先读回原 ID 的持久事实。原 run 已 completed 时重复对账只读取事实，不能再次写授权；否则“成功后已清空→重启又看见 completed→重新发放”仍会复活已结束的删除权限。

单 executor 在上一授权结束后才开始下一持久候选，故正常路径不会覆盖尚未处理的授权。发放事务必须检查旧三字段全 NULL、没有 deleting；发现不符合时不覆盖、不合并、不借新成功扩大旧范围，保留明确事实交对账处理。源租约收尾错误不撤销已经提交的成功，也不重复发放。

### 3.2 每个新删除认领只使用有限权限

令活跃授权阈值为 `Ka/Ba`，当前策略为 `Kc/Bc`，每次新认领取：`Keff=max(Ka,Kc)`、`Beff=max(Ba,Bc)`。这是两种限制的共同保守边界，不会比任何一方更严。不得换用 run 准入时冻结的 keep/max，也不能将当前更严参数覆盖回授权字段。

1. 在事务和 manager 锁之外有界检查根、成员、真实字节和 guard；对<=64个已登记目录工作，不扫描全盘。计量含已知自有元数据、残留和未收尾 deleting；未知占用令 usageComplete=false，不能按0计算。
2. 按 `run_seq` 从新到旧确定目标保留集合，最高序号且实际核验有效的一份必为 guard；在数量/字节阈值内尽量保留更新的前缀，guard无论大小始终保留。其它残留消耗字节预算，不作为有效恢复点。不得因为最老的删除候选正被下载，就改删本来属于目标保留集合的更新文件。
3. 对目标集合之外的一个确切候选验证 completed、store/owner、成员与摘要/身份；在同一 mu 内确认下载租约为0，再在短事务复读授权 token、当前策略 revision/值、guard/候选状态及相关元数据。若决策快照已漂移则丢弃并重算，不能拿旧列表直接 CAS。
4. 条件仍成立才 CAS retained→deleting；此提交是**该确切文件的不可自动撤回删除认领点**，检查 RowsAffected=1。释放锁后做受控删除，不把 hash、SQLite或文件 I/O 放进事务。
5. 删除及目录消失均被确认后，短事务 CAS deleting→deleted，再重新计量/选择；本条未收尾前不认领下一条。不把仅有一次 unlink成功当整份删除完成。

策略 PUT 与步骤4由短事务顺序决定先后：若 PUT 先提交，须按其 revision/新值重新判定；若删除认领先提交，随后编辑或禁用不撤销这个已经落盘的确切清理意图。认领后策略再放宽也不能承诺恢复已删成员。`enabled`只控制计划准入，禁用操作本身不发放/重开轮转，不是已提交删除的回滚按钮。

因此“编辑不立即删除”的精确含义是：编辑不会发放新权限，变严不会使旧授权多删；原来已经授权或已经认领的清理仍可能在编辑后结束。若产品要求编辑/禁用立刻撤销所有未完成删除，则需另一套取消/恢复协议，不是本最小方案。

### 3.3 授权结束必须落盘

必须先收尾所有 deleting，再在正常可核对的根上确认以下一种情况，才能在短事务中按原 token CAS将三字段一起清 NULL：

- 当前实际保留与已知自有字节满足 `Keff/Beff`；没有目标集合外被租约跳过、删除失败或身份不明的待处理对象。正常保留集合内仍有下载不妨碍结束。
- **guard下限**：只剩一份实际有效 guard及其必要元数据，无其它可删对象、未知占用或未收尾删除；超额完全来自该 guard 本身。即使其字节大于 Beff，也结束本次授权，保留 excessBytes和“唯一有效备份不可再减”的受控原因。

CAS结束事务再次读取当前策略 revision与活跃 token；若变化就重算，不得以旧判断清除后来的授权。最后一次 deleting→deleted和结束检查可以同一短事务完成，但文件 I/O必须已经结束、guard/根核验仍有效；不能在删除真正完成前清 token。

guard下限不是永久积压。不得保留一个永远不允许删除的 guard 作为永真 retentionPending，从而永久阻止未来可能更小的新候选。授权清空后，仅因更严编辑造成的未应用差距或 guard下限超额，不构成“已有待续轮转”；下一份候选仍须单份预算、真实源/目标卷余量、64条 ownership硬限额和根安全条件。允许这一次新候选的临时双份空间，新成功重新授权后先处理积压，再生成下一份，不能连续叠加候选逃避上限。

根离线、无有效guard、usageComplete=false、下载阻挡或删除错误都不能冒充“已结束”；保留原授权/ownership并报告原因。守住最后一份与真实状态优先于宣称保留目标达成。关闭计划不会清空授权，也不删除其凭证来伪装积压消失。

## 4. guard、租约和崩溃重放

| 接缝 | 精确处理 |
| --- | --- |
| last-good指向坏/缺失文件 | 它只是候选。对非 deleting 的 retained文件重新寻找最高序号且实际核验有效的guard；hash/schema/SQLite/身份不成立的不能充数。找不到则停止新认领和后续破坏性步骤，不把 deleting或半删候选当guard。 |
| guard在长检查或收尾前发生变化 | 复核根/句柄/文件身份；必要时在<=64条内重新验证另一份完整guard。没有有效guard就保留材料、暂停。此协议不声称能防止外部瞬时介质损坏或同权限持续篡改，但不因自己的删除将有效恢复点主动降到0。 |
| 候选有内部下载/HEAD租约 | 不改变候选状态，不删除它，也不改删受保护的新文件。授权保持待续；最后一个租约关闭后仅唤醒既有executor。wake本身不提供授权，NULL时立即结束轮转尝试。 |
| 认领与新下载竞争 | 同一mu串行租约增加与retained→deleting；谁先成功决定。deleting禁止新下载。持久下载仍不占S03.1的快照全周期锁。 |
| 内部租约为0，但Windows外部句柄/ACL/卷错误导致删除失败 | 保留deleting、原授权和精确ownership，保存安全中文错误/真实字节，不恢复retained假装完整、不丢记录解额度。既有executor有界重试，不制造新run/队列项。 |
| 崩溃在成功事务之前 | 未见提交成功，不基于文件名字/last-good授权；按原发布对账，只有真正新的completed转移才原子发放。 |
| 崩溃在成功事务后、第一条删除认领前 | 三字段非NULL，重新核验guard与根，按授权和当前策略的较宽组合继续；不重新生成备份来获得同一授权。 |
| 崩溃在retained→deleting提交前/后 | 提交前没有删除许可，不能先动文件；提交后state是本条确切删除意图。授权字段不能先被清空，重启先收尾该条，再选择别条。无授权却有deleting是协议不一致，不能猜last-good补授权。 |
| 部分成员已删 | 只重放已登记确切成员，缺失只算该步已完成；核验剩余成员，owner最后删、空目录最后Remove。未知成员/链接/已检出的身份替换一律停止，禁止RemoveAll或按前缀扫删。 |
| owner已删、目录仍在的最窄窗口 | 仅在受控根、确切已登记deleting意图、普通且确认为空的目录上允许空目录Remove；非空/不明身份绝不递归。重启跨物理实体证明仍受marker逻辑身份边界约束，不能声称从已消失owner证明了未发生离线克隆。 |
| 目录已删、DB仍deleting | 先确认根整体可用且对应确切目录确实不存在；再补deleted。根卸载导致的NotExist不能当作删除成功。 |
| 崩溃在最后删除后、授权清空前 | 重放计量与结束检查，再CAS清空同token。不能无条件再删一条来“消费”授权。 |
| 授权清空后重启/旧租约wake | 不因新策略更严、completed仍存在、last-good非NULL或excess>0重开；只有下一次新的成功状态转移能发放。 |

授权终止前来源元数据受保护，部分删除的state/owner/摘要均沿用原表；不需要每成员进度表。缺失成员是否完成依赖受控根及该确切删除意图，而不是依赖文件名匹配。Commit或rollback未知时先读取原token/文件状态核对，不能盲目补发授权或继续越过认领点。

## 5. 状态展示与新生成准入

- `retentionPending`表示三字段非NULL或存在未收尾deleting；与“当前配置计算出的excess”分开。授权NULL但变严编辑尚未应用时，excess可以大于0；不得用excess反向启动轮转，也不得谎称新策略已应用。
- guard下限结束时 retentionPending=false，仍保留真实 ownedBytes/excessBytes和安全原因；不是usageComplete=false，也不是轮转成功达到字节目标。备份completed事实不改为failed。
- 已授权但租约/删除错误未消化、未知占用、根/guard无法证明安全时阻止新的持久目标生成。授权已结束后的策略差距/单guard超额不单独阻止更小新候选，仍执行现有每份、余量和ownership上限，不预删旧材料换空间。
- 故障原因使用已有受控状态/错误字段与中文日志；这份研究不新增前端字段。实现/UI冻结时须确保“等待授权应用”和“有授权但被阻挡”不会用相同一句“目标已满足”掩盖差异。

## 6. 反例与待验矩阵

反例A：已有7份、keep=7，一次成功后的轮转已结束，但last-good仍在。用户改keep=1后重启，若只查last-good就删6份，违反“编辑不删”。正确状态是授权全NULL，重启和租约wake都不得发起新认领。

反例B：一次成功按keep=7授权，但旧候选因下载暂停。用户改keep=1，若续跑直接使用当前值，就把旧授权扩成可删到1份。正确计算Keff=max(7,1)=7；结束后不重开，待下一成功才授权1。反向改为30时按30少删或结束，不能继续机械删到7。

反例C：唯一有效guard为100MiB、当前/授权上限为64MiB。如果“超额就永远pending”，即使后来源库已缩小至20MiB也永远不能生成替代备份。正确做法是结束该次不可再减授权、显示36MiB及元数据对应的真实超额，允许通过单份/真实空间检查的20MiB新候选；新成功授权后再删旧100MiB，不能为新候选先删唯一guard。
