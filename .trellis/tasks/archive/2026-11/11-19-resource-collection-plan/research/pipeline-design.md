# Research: 多来源资源收集闭环、任务归属与发布边界

- Query: 首期同时覆盖影视/动漫 RSS 与 BT、网页音视频、自有音乐、本地与远程文件导入时，如何复用现有下载和媒体能力，并保持任务恢复、来源去重、只读原媒体和受管发布约束？
- Scope: internal / architecture proposal；只读仓库与既有计划，未实施、部署或运行行为测试。
- Date: 2026-11-19
- Task directory: `.trellis/tasks/11-19-resource-collection-plan/`（父代理显式指定的新任务；读取时 `.current-task` 仍为旧插件计划，不据此向旧任务写入）。
- 用户补充范围: 首期选择“多种来源一起做”，接受更多工作量；可拆 PR，但 RSS/BT、网页、自有音乐、本地/远程导入都是首版出口，深度接管外部自动化工具可后续。

### 2. 首版建议的统一流程

```text
RSS / Torznab手动搜索 / magnet或torrent / 网页链接 / 本地选定目录 / 已配置远程存储
                         |
                  来源校验与有界发现
                         |
             持久候选 + 规则匹配 + 去重/缺集判断
                         |
           人工确认，或已显式开启的自动订阅规则
                         |
                 持久收集请求/任务
                         |
           +-------------+-----------------+
           |                               |
      既有 BT 协调器                受控获取 worker
      仍管 qB 选集/归属          网页 / 远程copy / 本地copy / 音乐副本整理
           |                               |
      原 staging/complete             私有 inbox / 每任务工作目录
           |                               |
      原下载发布门禁                 验证清单→批准发布→最终目录核验
           +---------------+---------------+
                           |
               通用收集进度投影 / 已发布内容
                           |
                复用媒体扫描→实际条目覆盖确认
                           |
                   imported + 原 ReaderDialog
```

这是职责图，不要求为了该需求重构全部下载/媒体代码。最小新增 collection 协调器和 acquiring worker，保留已验证 qB 调用、选文件及发布流程；把可供内部调用的创建/查询下载能力做小范围服务化，而非后台调用自己的 HTTP API。

### 3. 状态分层：界面统一，事实来源保持清楚

建议持久记录三个相互独立的维度：

1. **发现/决策状态**：`new / matched / review_required / approved / rejected / duplicate / expired`。来源条目不是执行任务，重复 RSS 刷新也不能重复派发。
2. **获取状态**：`queued / preparing / awaiting_selection / running / paused / completed / failed / cancelled / recovery_required`。统一 DTO 附 `executorKind`、`externalTaskId`、`lastObservedAt` 与不可用原因；BT 的事实仍来自现有 `downloads`，网页/复制由专用获取任务负责。
3. **入库状态**：`pending / verifying / publishing / queued / scanning / imported / failed / target_missing / no_supported_files`。完成传输并不等于允许播放，完成一次扫描也不等于预期文件已入库。

每个可变任务带 `revision`；命令有 `requestId`，相同 ID+不同参数必须冲突。页面用阶段及已证实字节/文件数显示进度，没有总量就不造百分比。网络离线显示旧快照；保留已经核验的本地内容。

**取消**：先持久化取消意图，再停止当前执行；没有回收 worker 子进程/写句柄前不允许重试或删工作目录。任务已发布后取消获取不隐式撤销已入库内容。不可安全取消的发布步骤明确返回状态，不报假取消成功。

**删除**：来源停用只停止发现；订阅停用只停止新派发；任务移除默认归档保文件；真实文件清理属于单独具名操作，首版不必提供“删除媒体文件”。

### 4. 资源身份和去重不能合成一个标题字段

建议分开建模：

| 身份层 | 建议键与语义 |
| --- | --- |
| 来源条目 | `sourceId + sourceItemIdentity`；RSS GUID/受限来源标识不足时使用稳定规范化摘要；修改标题不产生新下载 |
| BT 内容 | 复用现有 v1 SHA-1/v2 SHA-256/hybrid alias；引擎短 ID 视为不透明，不自行猜算法 |
| 网页资源 | 已验证 provider + 内容 ID + 导出 profile（视频/仅音频/质量范围）；首版单链接单条目及有界显式批量，不递归展开播放列表；URL 去掉敏感查询不意味着可以随便去掉影响内容的查询 |
| 本地文件 | 已注册来源根 ID + 规范化相对路径 + 可观察版本（size/mtime）；仅是观察身份，不能冒称字节内容哈希 |
| 远程文件 | remote ID + 对象路径/提供者对象 ID + 提供者版本/etag（若已证实其语义）；未知版本不伪造恒定 ID |
| 作品 | 用户确认的电影/剧集/艺人/专辑身份；存在外部元数据 ID 时同时保存来源命名空间；没有 ID 时保留未识别状态 |
| 发布版本 | 作品、集号、语言、画质、编码/音频等候选属性，不同发布可能指向同一作品；相同标题不自动合并 |
| 执行 | `collectionRequestId` 对应一次不可变获取计划；关联已有 `downloadId` 或 `acquisitionJobId`，成功后保存目标 item 关系 |

跨来源先依据确定身份合并别名；同算法已知 hash 冲突不能合并。弱相似标题仅提示“可能重复”。强身份去重和人工拒绝记录保留独立审计，避免重复刷新又进入待确认。

订阅判定至少保存作品/季/集或绝对集号、发布组/语言/质量、目标库及已有覆盖。解析不确定、SP/OVA、合集、跨季、季包、集号缺失及绝对集数尚未映射进入人工确认，不能靠文件名相似度自动下载。首版默认候选待确认；只在用户明确开启且规则无歧义时才允许自动提交和自动选文件。自动选择须先修订 download contract，仍使用完整实际文件清单、版本和锁定选集，不默认全选，不跳过 qB 选集安全性；遇到未匹配/混入文件回退待确认。

### 5. 持久化与恢复建议

建议的实体职责（最终名称可按项目风格收敛）：

- `collection_sources`：来源类型、名称、启停、调度/网络策略、根/remote 引用、credentialRef、配置修订、最近成功/失败、游标；公开 API 不返回秘密。
- `collection_subscriptions`：作品/关键词及规则、目标库、确认模式、质量/语言/发布组和集范围、规则修订。
- `collection_candidates`：来源条目和非敏感展示元数据、作品/发布属性、判定及理由、最后观察；不持久化短期手动搜索 token 作为唯一执行依据。
- `collection_requests` / `collection_operations`：不可变计划、幂等签名、revision、outbox、执行归属、重试时点/次数、关联 BT 或获取任务。
- `acquisition_jobs` / `acquisition_files`：非 BT worker 的实际执行观察、受限工作目录、不可变输出清单/尺寸/版本、发布证据；只读既有 BT download projection，不复制其事实表为第二权威。
- `collection_item_links`：获取任务与目标媒体 item 的关联和覆盖状态。作品解析在首版可按最小需要保存，不要求同时重建所有媒体元数据体系。

目前主库为 v2。以实施时实际最大版本追加迁移；旧插件计划也建议 v3，所以不能硬编码两个独立 `schemaV3`。新表不能重建原用户/媒体/下载数据；升级前后验证 IDs、收藏、进度与已发布下载清单保持。

**持久 outbox**：先短事务保存获准计划和唯一派发键，再网络/文件执行；迟到响应仅在 revision 符合时绑定。BT 已发 add 不重发，复用原归属对账；worker 请求超时则查询原 task ID / 所属工作目录对账，不立刻新建第二个任务。恢复只能接续本实例确实拥有的任务。

**RSS 游标**：建议按条目幂等入库后才更新成功游标；解析/网络失败保留上一份已知条目；首次订阅提供回看窗口/只收新增选项，避免无界补历史。正常刷新不重新获取已经拒绝、成功或正在执行的相同计划。

**预算建议，待首版实现测量定稿**：RSS 受限响应/条目数/嵌套深度/截止时间；全局和每来源并发、刷新间隔、发现保留量、每规则单轮新增量；获取全局并发、每任务字节/文件上限、带宽上限、磁盘预留和重试上限。所有参数要有中文解释。播放请求不受获取队列饥饿影响；禁止无界播放列表、无限 RSS 回溯和一轮启动全部历史条目。

### 6. 目录所有权与只读媒体兼容

#### 6.1 目录分工

- **现有媒体根**：应用保持只读；用户的本地音乐/影音只能登记扫描，或者明确复制到新导入根后整理。不得在这里写标签、改名、move 或执行 remote sync。
- **BT staging/complete**：继续归现有下载协调器/qB；不能让网页/远程 worker 写入其中，也不能让外部整理器重命名其文件破坏已锁清单、做种或发布基线。
- **收集 worker 工作区**：单独持久根，`inbox/<opaque-task-id>` 每任务隔离，包含获取中与 `.partial` 文件；不在普通媒体扫描根内，不将任意父目录挂载给 worker。
- **收集 published 根**：新受管输出，只允许 worker 按批准计划发布；主应用只读挂载并核验，通过新 acquisition publication registry 授权，媒体扫描/文件/封面路径共同检查。
- **音乐整理工作区**：只处理导入副本，完成后同样走清单发布；源音乐保持字节不变。

主应用需要新受管根的只读视图，写权限集中到受限 worker。已有 `downloadGate` 不可仅改成“complete 目录下都允许”；可新增并列的 collection gate/registry，在所有扫库、直接文件、封面缓存路径统一调用，原 BT gate 保持原语义。历史已发布清单在禁用 worker、停用来源、任务归档后继续有效；修改/重写中的新版本先撤销发布。

#### 6.2 写入与发布协议

建议获取过程先写私有临时路径，完成后 worker 上报受限相对路径清单；控制面根据批准根、任务归属、文件数/类型/尺寸预算审查；worker 在受控根内执行可恢复发布；主应用通过自己的只读根再次检查真实常规文件、父目录不逃逸、尺寸及版本，最后原子提交发布标记和清单基线。若跨文件系统不能把多个文件的搬迁误报为瞬时成功；目标仍隐藏，全部完成且核验后才开放扫描。

首版本地导入默认 **只读登记已有目录并扫描**；只有用户按需选择归档时才复制到受控导入根。远程导入使用 **copy，明确不做镜像删除的 sync**。音乐如需标签整理，同样先复制副本再改副本；默认登记不改原标签。同名目标不覆盖，由任务 ID 隔离，再由作品归并形成逻辑展示。

硬链接不作为首版默认：它与原文件共享内容，音乐标签修改会影响原文件；跨卷又不适用，还需单独验证权限/链接语义。未来仅对保证不改写的内容、实际同卷能力验证及显式策略开放，不能用“节省空间”覆盖只读源契约。复制也不能承诺零拷贝；不通过主 Go HTTP 进程整文件缓冲或全片 hash。

#### 6.3 路径映射

API 只接已注册 root/remote ID 与相对路径，不接浏览器任意绝对路径。明确 `workerRoot`、`appReadRoot`、`engineRoot` 的对应关系；预检同任务测试文件可见性/预期设备和权限，在 Linux 校验 mount 别名，Windows 校验大小写/设备名/尾随点空格和 reparse point；外部服务报告的 `/data/...` 不能直接当成本机路径。

### 7. 首版多来源 worker：权限、启动和平台能力

**必须交付的职责**：网页获取、远程复制、本地复制和音乐副本整理的受控执行及状态查询；这些首版出口不能仅给“打开 MeTube/rclone 页面”而宣称闭环完成。第三方自动化工具深度接管可后续，基本 worker 不依赖通用插件安装系统。

建议使用一个窄协议获取 worker（独立进程或服务），由受审核的固定适配器调用已配置工具；不开放任意 shell、原始 argv/Compose/二进制 URL。任务计划只包含来源 ID、已验证链接/对象、受限输出 profile、根映射和预算；工具参数由服务生成。所有凭据走受限文件/专用秘密通道，不放命令行、事件或主库普通备份。

- **Linux/NAS**：独立可选 Compose 服务/镜像，将工具、私密配置、工作区写权限放 worker，主应用仅只读 published；没有 Docker socket 和宿主全部媒体卷。需要跟随本项目管理时提供显式启动/停止及归属；连接用户已有独立 worker 则只调用 API，不拥有其进程。
- **Windows 原生**：既有媒体能力可独立运行；首版若承诺本地网页/远程获取，则必须交付固定已验证原生工具适配或允许连接具备相同协议的外部 worker，而不能显示一个不可工作的占位按钮。原生子进程依照现有 Job Object/进程树归属、取消、退出释放文件契约；不能按进程名杀工具。
- **Windows Docker Desktop**：支持范围仍是现有本地 Linux amd64 模式；新增 worker 的 Compose、固定镜像/许可清单、卷角色、启动校验器和完整停止协议必须同步修改。只改 YAML 会被当前精确校验拒绝。
- **能力查询**：分别返回 RSS、BT、网页、remoteCopy、localCopy、musicOrganize 的 available/reason、执行节点 OS/arch、协议版本和就绪；以服务真实探测为依据，无 GET 自动安装/启动。
- **完整退出**：本实例拥有的 worker 要停止接收、持久化任务、回收受管写进程、等待 DB/文件释放后才报告成功；用户外部 worker 不自动停机，但本应用需停止轮询并保留可恢复任务。首版需说明关闭应用后哪些获取继续执行。

**首批平台选择建议**：先把 Linux/NAS 独立受控 worker 作为五类来源的完整参考实现；Windows 原生优先连接这个协议一致的远程 worker，不把当前仅 Linux 的固定 qB/Jackett 引擎助手扩展成通用工具执行端。Windows 本地原生工具包可后续作为同协议的另一执行节点；首版支持文案应明确“Windows原生+已配置worker”，不能只写“Windows原生支持全部获取”。远程连接使用专用受限凭据、精确端点与 TLS（受信任内网部署策略另行明确），不转发主应用Cookie，不接收任意命令；连接是新增能力，不放宽当前Docker Desktop本地上下文限制。

| 参考部署 | 来源与发布映射 | 停止语义 |
| --- | --- | --- |
| Linux/NAS同宿主容器 | worker读来源根、写私有inbox/published；主应用只读相同published物理根，容器路径允许不同但映射须预检 | 项目拥有的worker纳入显式完整停止；保留数据卷和持久任务 |
| Windows原生连接Linux/NAS worker | Windows本机路径与Linux路径不能直接互换；需用户预先提供worker可读的共享来源以及双方可见的published根，按rootId建立确定映射。若输出在NAS，主应用必须已挂载相应只读共享根；若来源只在Windows D盘而worker不可见，拒绝派发并提示补足映射，不假报成功或自动上传整目录 | 用户管理的外部worker继续运行，应用退出停止本地API/轮询；恢复后按远端taskId对账。若未来接管远端生命周期须另行授权与所有权契约 |
| Windows Docker Desktop项目整包 | 新增固定worker镜像、独立配置/数据/工作区卷，主应用只读published卷；保持现有Linux amd64与本地context验证 | 精确Compose验证器、镜像manifest/许可清单、卷角色、实际运行检查、owned worker停止和105秒引擎停止链路一起更新；只有这些全部通过才能声明整包完整停止 |

映射预检不仅校验字符串：在受控worker根生成专用小探针，主应用从对应只读根读取并核对任务nonce，再清理仅属于该探针的文件；不能改写用户媒体来验证映射。针对路径/卷不可见的部署，状态为配置不可用，其他已准备来源仍可运行。共享目录权限、跨主机网络和NAS吞吐属于真实部署验收，fixture不能替代。

工具自身的 API、支持网站和平台版本应由来源研究核验；本研究不把“有 CLI/容器”当作已经可在所有目标系统运行。

### 8. 网络、凭据与不可信内容边界

- 收集来源可编辑记录和原手动 Torznab只读配置的关系要明确：首版推荐保留原配置兼容，新增收集来源独立管理，并允许引用现有来源 ID；不静默迁走或覆盖 qB/Jackett 的原秘密文件。
- 公开候选和日志仅包含来源 ID、脱敏标题、结果数量、阶段、耗时、任务 ID；不包含 raw RSS XML、下载 URL、magnet、私密 GUID、apikey、Cookie、令牌、remote配置或工具原始 stderr。
- 含凭据 RSS/网页 URL、短期下载 locator 与远程授权保存在受保护私密配置/引用中；主数据库/普通备份保存公开元数据和引用。恢复备份后缺少秘密应标记需重配，不能假装可运行。
- RSS XML 拒绝 DTD/外部实体并设条目、深度、字节与超时预算；不把 description HTML 或来源封面直接作为主页面活动内容。URL/rclone对象名/文件名均是不可信输入。
- SSRF 防护必须在**真实发请求的组件**执行：显式允许内网的 Jackett/自建 remote，网页下载默认只允许经过策略的公网 HTTPS；逐次验证目标/重定向，不泄露跨域认证。外部下载器可能自己跟随多域/CDN链接，父进程仅对入口 URL 做一次 DNS 校验不构成完整网络边界；worker 需实际受控代理/egress策略或经核实等价方案，做不到的能力应明确限制，不能宣称已经防护。
- 远程只允许已配置的具名 remote 和批准子路径，不允许浏览器输入任意连接字符串/额外 flags，不挂载为核心文件系统，不执行 destructive sync，不删除用户云端对象。
- 现有搜索 token 的约束不扩大为任意 torrent resolver；新 RSS 解析和下载 locator 是专用受限解析器，继续复用原 bencode/magnet安全校验后交给 qB。

### 10. 必须覆盖的失败案例与验收

1. **发现/重复**：同 RSS 重复100次仅有一个候选和一条有效派发；同标题不同 hash 不合并；不同来源同hybrid内容合并alias；首次大量历史条目不能全部自动启动。
2. **规则/自动化**：缺集规则识别明确集号；合集/OVA/集号冲突待确认；规则改动后旧revision迟到结果不触发新规则任务；自动选择仍验证完整清单。
3. **派发不确定**：BT add / 网页worker start接收后响应丢失，重试/重启只对账原ID，不产生第二份下载；外部相同hash返回冲突不接管。
4. **输出发布**：网站报告成功但只剩 `.partial`、尺寸改变、symlink/reparse point、源目录逃逸、目标跨卷搬迁未结束，都不能被扫描、播放或命中旧封面；只公开通过验证的清单。
5. **本地/音乐**：自有音乐原字节/标签/路径不变；整理只改副本；同名文件不覆盖；硬链接不偷偷用作可写音乐副本。
6. **远程**：copy取消/掉线不删除源或目标既有数据；凭据过期显示需认证并保留进度；对象更换版本后旧发布基线不能冒充新对象。
7. **入库**：获取完成但目标库删除→`target_missing`；扫描已经越过新目录→有界补扫；无支持格式→`no_supported_files`；独立重试入库不重新下载；成功必须存在目标 item 链接。
8. **队列/退出**：来源大量候选和web有界批量遵守配额，播放列表链接不能递归展开；低空间暂停仅本实例任务；退出/取消回收本实例子进程与文件句柄，重启恢复一次；不停止用户外部服务。
9. **安全**：跨源凭据/日志/API/数据库快照无秘密；SSRF/重定向/URL用户信息/metadata目标被实际执行层拒绝；XML炸弹、超预算输出、路径注入、Windows设备名和恶意工具回执被拒绝。
10. **既有回归/UI**：五种媒体、鉴权/同源、BT选集与发布、断网快照、>4GiB Range、收藏和进度保持；手机仍五入口，收集从更多；375/768/1024/1440、两主题、键盘/焦点、取消旧请求和单请求轮询。

实施验证遵守 `python -B scripts/project_env.py -- ...`。新增临时单元测试执行后清除，保留可复用集成验证脚本与 `docs/verification.md` 真实执行证据。本研究未生成测试、未运行构建/行为测试、未连接来源或部署worker。
