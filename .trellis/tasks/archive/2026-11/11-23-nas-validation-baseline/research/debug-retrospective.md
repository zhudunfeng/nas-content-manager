# S01 编排边界复盘

## 1. 根因分类

- D（覆盖缺口）：最初自检验证了部分帮助函数，未覆盖真实 CLI 分派、版本探测和最终清理中的异常路径。
- C（传播遗漏）：清理错误已在命令层记录，但调用者仍可能按缺依赖归类；一次补丁曾位于主入口退出语句之后，语法检查无法证明其可达。
- E（隐含假设）：把绝对路径当成无空格的 Windows/常见 POSIX 前缀，把链接安全检查当成单次根检查，遗漏 UNC、其他 POSIX 根和逐级重解析目录。

## 2. 为什么局部修复不够

仅扩大正则前缀不能完整遮蔽含空格路径；对序列化 JSON 做替换还可能破坏 JSON。只检验进程退出码不能发现收尾失败后命令证据丢失；只测试根创建函数不能发现 self-test 的异常在入口处理之外逃出。故修复必须从入口、执行、清理到持久证据贯通断言。

## 3. 已采取的预防

| 优先级 | 机制 | 落地位置 |
| --- | --- | --- |
| P1 | 结构化递归脱敏，路径含空格/UNC/POSIX 扩展断言 | 两份 baseline 脚本 |
| P1 | 创建前拒绝 Windows 路径别名，逐级剪枝链接/重解析目录 | baseline 路径与日志遍历 |
| P1 | 清理失败优先 failed，保留命令退出码与日志 | 命令、工具、self-test 收尾 |
| P1 | 真实 CLI 子进程断言非法根 exit2，故障注入检查清单 | 长期 self-test |
| P2 | 将以上行为写成可执行规范，独立复核后记录最终实跑结果 | backend/baseline-contract.md、quality-review.md |

## 4. 扩展检查与边界

本轮检查扩展到同一编排器的 core、领域命令、工具版本、target JSON 和自检收尾，不据此声称已审计所有历史脚本。最终结果以 implementation.md 和 quality-review.md 的实际执行为准，保留失败运行证据。后续 schema/API 改动继续用完整入口回归，不能用语法/包编译代替业务断言。
