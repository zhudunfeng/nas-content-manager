# BT 种子下载与媒体入库

## 1. 目标与本次交付

在栖库中完成“添加磁力／种子 → 下载 → 自动入库 → 播放或阅读”的闭环，覆盖视频、图片、漫画、小说和音乐。沿用现有界面风格与管理员登录，优先考虑易使用、易部署、超大文件和源文件安全。

2026-11-17：规划交付后，用户明确要求“按计划实现代码”，P1–P4 已获授权并进入实施。当前交付目标为业务代码、可选部署配置、文档与非 Docker 验证；不运行 Docker、不自动提交 Git。以下验收项仅在取得相应执行证据后勾选。

## 2. 当前项目事实

- Vue 3 + TypeScript + Vite；Go 标准 HTTP、SQLite、FFmpeg／ffprobe。
- 实施前数据库为 v1，已有五类索引、收藏、标签、进度、扫描／增强任务与一致性备份；本次增量迁移为 v2。
- 默认单应用容器，`/media` 只读，`/data` 保存本地 SQLite；下载是新引入的受控写入能力。
- `runScan` 定期遍历目录，不能仅在“下载完成回调”中排除未完成文件；所有扫描入口都必须经过发布门禁。
- 当前写请求全局限制为 64 KiB，不能直接承接 `.torrent` 文件；上传接口需要独立的有限额度。
- 现有 `jobs` 有媒体库外键，专门表示扫描／增强任务；不适合承载持续数小时的 BT 传输。
- 音乐代码已提交为 `a338021`；原任务保持 review，本任务独立推进。
- Docker 构建与部署由用户手动验证；不以自动运行 Docker 作为实施完成条件。

## 3. 已批准的实施决策

**栖库负责界面、认证、编排和入库，qBittorrent 负责 BT 传输与做种。** 后端通过独立适配器调用其 WebAPI，浏览器只连接栖库。

| 方案 | 取舍 | 当前结论 |
| --- | --- | --- |
| qBittorrent WebAPI 集成 | 独立进程承载下载与校验；可复用现有实例，也可增加可选容器；需要适配 API 和初始化凭据 | 推荐首期 |
| Transmission RPC 集成 | 可行的替代引擎，但另有 RPC、认证与状态映射契约 | 保留适配器边界，首期不实现 |
| 内嵌 Go BT 引擎 | 表面上维持单进程，但协议资源、恢复、做种与文件管理均成为本项目责任 | 不作为首期方案 |

aria2 的多协议方向与本次 BT 首期目标不同，比较记录见研究文件；不为未来可能的 HTTP 下载预先引入第二套引擎。

### 部署默认

1. 已有 qBittorrent：连接现有实例，仅管理栖库创建的任务。
2. 没有下载器：使用可选 Compose 扩展增加官方 qBittorrent 容器；基础 Compose 继续只部署栖库。
3. 新容器保留首次设置固定 WebUI 密码的步骤；官方镜像的首次临时密码流程不能被虚构成现成的密码环境变量。初始化使用受限入口，随后关闭不需要的 WebUI 宿主端口。
4. 首期按 qBittorrent 5.x 适配，实施时锁定实际验证的稳定标签和镜像摘要、记录版本探测结果，不使用 `latest`；不宣称覆盖所有 4.x／5.x 版本。

## 4. 首期功能范围

### 4.1 添加与管理

- 单次添加一个 `magnet:` 或上传一个本地 `.torrent`，支持 BT v1／v2／混合种子的身份归一与去重。
- 选择五类内容之一。目标是该类型的**受管下载媒体库**；首次完成时可按用户在表单中的选择创建下载库，不向原 `/media` 写入。
- 展示名称、已下载／所选总大小、进度、上下行速度、连接数、分享率、预计剩余时间和最后同步时间；无有效速度时剩余时间显示“未知”。
- 支持开始、暂停、重新检查状态、失败恢复、移除任务；移除默认保留文件，首期不提供删除媒体数据的按钮。
- 有元数据后支持文件选择；选择完成前不进入正常载荷下载。磁力元数据获取需要单独状态，具体停止行为必须用锁定版本实测，不承诺网络零载荷；无法在确认前阻止正常载荷的版本不开放这条流程，不能偷偷退化为全包下载。
- 文件选择确认后锁定；首期不支持下载中／已入库后改变选集，避免复用完成标记或漫画目录时混入半成品。
- 同一请求重复提交返回同一任务；同一内容重复添加定位到已有任务。引擎中存在同哈希的非栖库任务时明确报冲突，不擅自接管。
- 做种与下载完成分开展示；入库不停止做种。沿用引擎的分享策略，只有明确属于栖库的任务才能被暂停或设置任务级限速。

### 4.2 下载完成后入库

- 以“所选文件确实完成、引擎不在校验／移动、最终路径正确、清单与本地文件核对通过”为发布条件；不以进度 100% 或一次 API 成功作为完成证据。
- 先下载至 staging，再由 qBittorrent 移动到同一下载卷中的 complete 目录；栖库不复制整份媒体。
- complete 中仍未 ready 的任务目录不得被任何手动／周期／重启扫描、封面探测、目录漫画枚举或媒体接口读入。
- 发布后复用现有幂等扫描和有界封面／元数据增强。漫画目录还须按所选清单枚举页面，不把未选文件的占位符当成漫画页。
- 下载状态与入库状态独立。失败时保留原下载，允许单独重试入库，不重新下载。
- 入库只纳入匹配当前内容类型及现有阅读器支持的文件。混合种子首期选择一种入库类型，其余文件可保留但不声称已能阅读；没有可导入文件时明确提示。
- 文件下载成功不代表浏览器能解码，也不绕过 CBZ、TXT、EPUB 等既有限额。

### 4.3 界面与交互

- 桌面侧栏新增“下载中心”；手机放入现有“更多”，底栏仍不超过五项。
- 复用石墨／青绿色明暗主题、SVG 图标、原生弹窗与焦点恢复。
- 下载中心采用清晰任务列表：顶部“添加下载”，状态筛选为全部／进行中／已暂停／已完成／异常；任务中同时显示下载与入库状态。
- 添加弹窗分“磁力链接／种子文件”，高级选项折叠；元数据加载、文件选择、重复任务和路径错误有独立中文反馈。
- 详情展示文件清单与选择、任务级限速、同步时间、中文错误和“查看入库内容”。
- 断开连接显示“下载器暂不可用，展示上次状态”，不假装速度实时或把所有任务标成失败。

## 5. 超大文件与可靠性要求

- 字节数、偏移和累计流量在 Go／SQLite 使用 64 位；前端禁止 32 位按位运算处理文件大小。
- 不经浏览器上传大媒体，不经 Go 中转 BT 数据，不整文件读入内存，不再算一遍全片哈希；BT 必需的分片校验由下载引擎承担。
- staging 与 complete 推荐同一真实文件系统，移动由引擎执行并等待结束；不同挂载可能触发复制，不能宣称跨盘零复制或瞬间入库。
- 独立下载实例配置保守并发与缓存，已有实例只使用任务级限速且不改全局策略，给现有播放和封面任务留资源；缓存、重校验与真实吞吐需在目标 NAS 验证。
- 下载空间预算与封面缓存空间预算分开；按所选剩余量及安全余量检查，下载中持续监测。空间不足仅暂停受管下载，保留进度，不自动清理数据；外部写入仍可能耗尽磁盘，不能承诺绝对预留。
- qBittorrent 的配置／恢复数据与下载数据均持久化；栖库重启先对账，不重新创建全部任务。
- 登录失败、掉线、进程重启、API 请求超时、移动未完成和挂载失联都有明确状态及有界重试。
- 网络调用不持有 SQLite 事务或原有 `App.mu`，不占满扫描 worker；下载器故障不拖垮基础媒体库或健康检查。

## 6. 安全与数据边界

- 使用现有管理员会话与同源写保护。qB 密码、SID、原始种子与磁力中的私密参数不进入前端响应或日志。
- 引擎地址和根路径由后端配置；禁止前端任意指定下载路径、任意访问 WebAPI 或上传远程种子 URL。
- 种子上传有独立总量限制、受控解析和清单预算；其他接口继续保持原 64 KiB 限额。
- 文件清单拒绝路径穿越、绝对路径和特殊／软链接条目；发布与访问再次验证规范化边界。
- 下载器只写专用下载根，不挂载原 `/media`；栖库对下载根也使用只读挂载。
- 原媒体库删除行为保持“仅删除索引”。下载任务归档也不能删掉已发布清单，导致既有内容失去门禁依据。
- 下载数据目录不得通过另一个媒体挂载别名泄漏 staging；不能证明隔离时阻止启用并给出路径修复提示。

## 8. 实施拆分

| 阶段 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| P1：引擎与数据基础 | 固定版本技术探针、认证／版本探测、受控路径、v2 迁移、下载实体／命令对账、关闭功能时的兼容 | 含重复提交与超时恢复的适配器契约明确；镜像初始化步骤可执行 |
| P2：下载管理闭环 | 添加与元数据选择、任务开始暂停移除、分页状态、断点恢复、资源／空间策略、基础下载界面 | 可在真实引擎样本上完成可恢复下载，且不影响其他引擎任务 |
| P3：安全发布与入库 | 异步移动对账、统一发布门禁、选集清单、五类入库与失败重试、详情跳转 | 完成与未完成场景均验证；原播放／阅读回归通过 |
| P4：交付与兼容 | 响应式细节、可选 Compose 扩展、凭据初始化与备份文档、回归结果 | 非 Docker 检查完成；用户获得独立 Docker 手动验收步骤 |

P1–P3 顺序推进，不在门禁实现之前把中间版本暴露给真实媒体库。具体改动位置、接口和状态机见 `info.md`。
