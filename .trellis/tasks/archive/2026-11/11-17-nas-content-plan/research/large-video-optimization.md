## Findings

### 1. 五个关键官方来源与证据

1. Go `net/http` 文档：https://pkg.go.dev/net/http#ServeContent
   - `ServeContent` 接受 `io.ReadSeeker`，支持 Range、条件请求与预设 ETag；通过 seek 获取大小。
   - `ServeFile` 提供文件响应与 MIME 判断，但接收文件路径本身不代表已经完成应用鉴权或媒体库目录授权。
   - 使用可 seek 的 `*os.File` 作为内容源，不应先读成 `[]byte` 或 `bytes.Reader`。
2. FFmpeg 格式文档：https://ffmpeg.org/ffmpeg-formats.html
   - MOV/MP4 的 `+faststart` 会进行第二遍处理，将索引信息搬到文件前部。
   - HLS 有分片时间、独立片段等选项；关键帧和 GOP 约束会影响实际片段切点，不能只靠目标秒数保证精确切分。
3. FFmpeg 主文档：https://ffmpeg.org/ffmpeg.html
   - 输入位置的 `-ss` 通常定位到最近的可 seek 点；重新编码并启用准确定位时，可丢弃目标前解码数据；stream copy 的边界与精确性不同。
   - `-c copy` 是流复制，不是重新编码；能否 remux 仍取决于目标容器、轨道与客户端组合。
4. FFprobe 官方文档：https://ffmpeg.org/ffprobe.html
   - 可用 `-show_format`、`-show_streams` 读取格式/轨道信息，可用 `-read_intervals` 约束特定读取区间。
   - 文档说明 seek 并非精确到请求时间；不得将探测区间当作严格帧级定位保证。
5. Matroska 官方 Cues 说明：https://www.matroska.org/technical/cues.html
   - Cues 是可选的顶层索引信息，用于 seek；其存在与组织会影响高效定位。
   - 因而 MKV 能否快速拖动依赖具体文件索引和播放器/解复用器行为，不能仅按扩展名判断。

补充核对 Go 当前实现：https://go.dev/src/net/http/fs.go 。以下协议验收基于标准库行为，具体项目在锁定 Go 版本后仍需回归测试。

### 2. 先分清瓶颈，不用文件大小直接决定转码

文件体积影响目录处理、完整复制/重写耗时和缓存空间；视频码率、码率峰值影响播放所需的持续/突发读取吞吐；实际可用网络带宽和 NAS 磁盘吞吐决定是否能及时送达；编码、分辨率、色深、字幕等决定客户端兼容性与转码成本。这些是不同维度。

- 低码率但时长很长的大文件，不一定需要转码。
- 高峰值码率的较小文件，也可能让无线网络或磁盘来不及供给。
- 容器/索引问题首先处理封装和定位；不能统一归结为机器算力不足。
- 首版不承诺固定起播、拖动延迟或 4K 转码并发；先定义观测指标，待实际硬件、网络、客户端和样本测试后建立目标。

### 3. 大文件 HTTP 路由：标准库 Range + 打开文件流

推荐流程：校验登录/媒体库权限 → 通过媒体 ID 查询受控路径 → 检查根目录和符号链接边界 → 打开文件并 `Stat` → 设置正确 MIME、验证器与缓存策略 → `ServeContent`。同一次响应使用已打开的文件句柄；外部替换/修改文件时需要失效旧元数据和播放会话，不假定只读挂载就能阻止其他程序改文件。

- 大小、位置、字节范围与数据库字段使用 64 位整数；Go 文件大小/seek 使用 `int64`。API 需要避免 JavaScript `number` 对超出安全整数范围数值的精度损失，必要时返回十进制字符串。
- GET 正常完整响应为 200；可满足的字节范围为 206，携带正确的 `Content-Range`、片段 `Content-Length` 与实际内容；不可满足范围为 416，并给出总长度语义。HEAD 不发送文件体。
- 测试开放范围、后缀范围、末尾字节、越界、`If-Range` 命中/失配和文件版本改变，不自行实现一套简化 Range 解析器覆盖标准库。
- 不要在 Range 之上套会缓冲完整响应的审计、中间件或压缩器。视频响应通常不再 gzip；请求日志只写元数据，不记录媒体响应体。
- ETag 必须代表对应文件版本。`ServeContent` 不会自动为源视频算完整强哈希；不要为了生成 ETag 在首次播放时通读整个超大文件。可优先用 Last-Modified/弱 ETag；弱 ETag 不能作为 `If-Range` 的强验证器。强 ETag 只用于确实可保证内容版本不变的衍生物或已有强内容标识，不把不可靠的 size+mtime 冒充强校验。
- 内容权限在每次媒体/分片请求执行，不因知道源路径或命中共享缓存而绕过授权。可采用同源会话或短期媒体凭证，日志隐藏凭证。
- 限制请求头、每用户并行读取、全局带宽/并发和任务数，防止大量小 Range 或并行连接耗尽 NAS。多范围策略要明确；不能把所有不支持的情况都错误返回 416。
- `ServeContent`/`io.Copy` 可流式工作，但不应承诺所有系统、TLS、HTTP 版本与中间件下都可零拷贝/sendfile；正确性和有界内存优先，实际优化靠剖析。

### 4. 播放决策：直放 → 必要时 remux → 必要时转码

**直放**：客户端支持容器、视频/音频编码和字幕时，直接提供带 Range 的原文件。文件再大也不应因此生成整份副本或整片 HLS。

**Remux**：编码可用但容器/轨道组合不适合浏览器时，可按需重封装并缓存；不重新编码视频，但可能涉及大量 IO。只复制流不能解决不受支持的编码或必须烧录的字幕。单独转音频也比转整条视频更合适。

**Transcode**：仅对必要的视频/音轨、分辨率/码率或字幕烧录做处理。硬件加速是可选能力，取决于设备与驱动，容器不默认开启特权模式；没有硬件能力时应说明限制/提供可用档位，避免占满 CPU 影响其他内容使用。

MP4 的 `moov` 在末尾时，Range + seekable 文件源可能让客户端先取尾部索引，但播放器、网络和文件结构会影响实际起播。不支持快速开始的文件可提供可选“优化播放副本”任务；`+faststart` 涉及第二遍搬移索引与输出文件写入，不是零成本修改一个标记。默认不修改/覆盖源文件，不自动为每个超大文件做完整重写；预估空间、检查余量、允许取消并清理临时输出，成功后再原子发布衍生物。

MKV 的 Cues、关键帧间隔、时间戳和字幕/音轨组合影响 seek。缺索引或异常文件可能需要额外处理，应显示明确原因与可选优化入口，而非全库扫描时自动重建所有索引。

### 5. HLS 与跳转：增强能力，不能当作所有大文件的前置条件

- HLS 适用于需要自适应码率、转码输出或特定客户端适配的情况。首版可先实现可靠原文件直放与 seek，HLS 作为按需增强。
- 对转码播放，按用户目标时间和附近可解码关键帧启动/复用任务，正确处理时间戳、音画同步、清单与分片映射。不能简单将任意 `-ss` 与 `-c copy` 组合承诺精确到帧。
- 输入侧 seek、解码丢弃和流复制有不同成本与边界；若首版不实现可随机访问的转码会话，就明确“该格式仅支持预处理后播放/受限跳转”，不要给出能够任意 seek 的假象。
- 缓存键至少包含源文件版本、编码/封装参数、字幕选择、处理器版本与时间段；不同档位和时间段不可误命中。
- 预取限定前向时间窗、片段数与字节预算，不因为首个请求就在后台转完整个 200GiB 文件。跨时间点跳转时取消或缩减旧窗口，避免同时转多个无人观看的片段区间。
- 设定总缓存预算、单会话预算、磁盘最低剩余空间、任务并发、空闲清理策略；活跃分片要固定保护，完成或失败后释放，不在读取过程中删除。清理按播放会话生命周期判断，不因某一个 HLS 请求结束就杀死整个会话。
- 以上预算是未来需要中文说明的配置项，具体数值应基于目标 NAS 测试，不在方案里虚构通用常量。

### 6. 扫描、探测与子进程资源保护

- 首轮扫描只做扩展名识别、路径/大小/mtime 等轻量 stat 和入库；随后受控 ffprobe、封面生成。文件大小不触发全片读取，不默认计算全文件 hash，不逐帧统计时长或生成完整关键帧列表。
- `probesize`、`analyzeduration` 和区间参数只能影响探测行为，不能简单承诺它们是绝对 IO 上限。某些容器可能 seek 到文件末尾读取索引；设置任务墙钟超时、并发上限与取消能力，失败保留“元数据待完善”，不阻塞整库可见。
- 封面选择少量候选时点，限制输出尺寸和次数；稀疏/损坏文件有超时与失败记录，不无限重试。
- FFmpeg/ffprobe 必须使用结构化参数数组启动，路径不能拼接进 shell。根据任务/会话取消信号终止子进程，提供温和退出与超时强制结束，回收子进程和临时目录；重启后作业按持久状态恢复。
- 监测应用进程/子进程内存、CPU、磁盘 IO、临时盘余量和活跃会话。忙碌时降低后台扫描/封面任务优先级；前台播放资源先于后台加工。
- 仅限制应用缓冲不等于限制所有机器内存：操作系统页缓存可能增长且可回收，FFmpeg 也有独立工作集；监测和验收应区分它们。

### 7. 最小首版与增强边界

**首版必须**：64 位文件元数据；鉴权与目录边界；`*os.File` + 标准库 Range/HEAD/条件响应；流式有界应用缓冲；原文件只读；支持已验证编码组合的视频直放、进度与 seek；轻量扫描、探测/封面限流与取消；诊断可解释；不因体积大自动转码/复制/全片 hash。

**后续按需增强**：remux 与 faststart 播放副本；按时间段的 HLS 转码会话、有限预取与缓存回收；硬件加速；异常索引修复；依据网络与客户端选择码率档位。

仍然使用一个镜像、一个 Compose 服务，FFmpeg 随镜像提供；不为超大视频强制增加 Nginx、Redis、MinIO 或独立队列。只有性能剖析证明必要，才考虑可选前置代理/专用服务。

### 8. 可测验收建议（候选样本，不是产品上限）

候选样本可包含约 20 / 100 / 200 GiB 的文件，分别覆盖常见 MP4、尾部 moov 的 MP4、带/缺 Cues 的 MKV、长 GOP、多音轨与字幕；对不兼容样本验证明确提示与增强路径。上述大小仅用于发现整数溢出和规模相关问题，不表示最大支持 200GiB，也不要求用户此刻提供样本或硬件。

1. **协议**：HEAD 无文件体；首部/中部/尾部 Range 的字节与原文件一致；206/416、长度与验证器正确；文件改变后不把旧片段混到新版本；无权访问时不得返回任何媒体字节。
2. **内存**：固定并发、同一播放路径下，分别读取上述样本，应用进程内存不随完整文件大小线性增长；记录 Go heap/RSS、FFmpeg 工作集与系统页缓存，不能把 OS 缓存直接误判为全文件加载。
3. **交互**：记录起播、10%/50%/90% 跳转、恢复进度耗时与失败原因；固定客户端/网络/格式后建立基线，暂不设脱离环境的毫秒 SLA。
4. **读放行为**：直放不创建整片副本、整片 HLS 或完整 hash；探测可超时/取消，短时间重复扫描不反复启动相同昂贵任务。
5. **负载保护**：多 Range/多会话、扫描和封面并行时不失控；断网/关闭播放、服务重启、磁盘不足、源文件离线均能回收或恢复，不能遗留不断运行的转码进程。
6. **增强验收**：若引入 HLS/优化副本，验证缓存预算、活跃片段保护、空闲清理、字幕变更缓存隔离、目标时间与音画同步；取消任务不会修改源文件。
7. **指标报告**：同时记录实际文件/视频码率、有效网络吞吐、磁盘读取、CPU/GPU 占用、温度/降频（若可获取）、起播/seek/错误率，依据证据确认瓶颈。

## Caveats / Not Found

- 未提供目标 NAS、浏览器、网络与实际样本，不能保证所有容器/编码均可直放，更不能承诺任意超大文件实时转码。
- Go 文档与 FFmpeg 文档只证明底层能力和限制；并不证明尚未实现的产品已经满足上述协议与资源约束。
- 文档没有业务代码、依赖版本锁定或基准测试；实施时需锁定版本并验证实际标准库/工具行为。
- 本文件仅为针对新增超大视频要求的增补，不改变原有四类内容、易部署与只读纳管目标。
