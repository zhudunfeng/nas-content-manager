# Linux/Windows 双平台与 Windows 一键启动：技术修改计划与实现依据

## 0. 双平台硬约束（用户已确认）

- 同一业务内核、同一网页/API/SQLite schema；Linux 与 Windows 只在入口、目录/权限、锁、工具定位和进程管理上做适配。
- Linux 保留现有 CLI、环境参数、原生运行与 Docker/bind 部署，支持无桌面服务器；不因 Windows 托盘/目录选择器而引入 GUI 依赖。
- Windows 专用代码使用 `_windows.go`/build tags；Linux 相应适配放 `_linux.go`，共享包不得无条件引用平台符号。
- Linux amd64/arm64 与 Windows amd64 同时构建；只有交叉编译结果时明确标注，真实运行与 Docker 验收按各平台/架构单独留证。
- Windows 本地盘符/UNC 与 Linux POSIX 路径分别规范化，路径列表仍遵守 Windows 分号、Linux 冒号；不全局字符串替换，不降低符号链接/junction/下载门禁校验。
- 权限适配按 POSIX UID/mode 和 Windows 当前用户 ACL 分别实现；不能在 Windows 直接忽略权限错误冒充校验通过。
- 兼容两种系统不等于可直接跨系统复制正在运行的 SQLite/路径数据；迁移必须停机/一致性备份，并显式重映射路径和实例配置。

| 平台 | 启动方式 | 业务能力与边界 |
| --- | --- | --- |
| Linux NAS/无桌面服务器 | 原生 CLI/归档包与现有 Compose；继续显示访问地址和中文日志 | 五类媒体及现有外接/托管引擎能力保留，现有 bind 模式不变 |
| Windows 11 x64 | 新增双击 EXE/托盘，原 CLI 仍可用 | 原生五类媒体；需要完整引擎自动部署时使用明确选择的 Desktop Linux 容器全栈 |
| 两端容器部署 | Linux 容器 app/helper/engines，同一私有网络 | 共享引擎控制面，Linux bind 与 Desktop 命名卷为部署存储适配，不分叉业务 |

## 1. 推荐路线与边界

复用双平台 Go/Vue/SQLite 和现有浏览器界面，增加一个 Windows 原生启动器。保持 Linux 功能完整的同时，先交付 Windows 普通用户免开发环境、免 Docker 的五类媒体入口，再以同一启动入口提供可选 Docker 全功能配置。原生模式本期不新增自动安装 qBittorrent/Jackett；完整 BT 托管通过 Linux 容器全栈提供，Linux 既有托管能力保持。

两种配置有独立实例 ID、监听端口和数据；启动器显示当前模式及数据位置，切换需明确选择，不暗中创建空库冒充迁移成功，不允许两个进程写同一库。已实现原生入口及Docker完整模式；后者要求维护者提供真实固定镜像清单，缺少时明确报错。

Windows 首个支持基线为 Windows 11 x64、当前受支持浏览器与本地普通用户；Linux 维持 amd64/arm64 构建目标及现有 NAS 部署范围。Windows ARM64、Windows Server 和 Windows 10 不纳入首批新增支持声明，需分别验收后开放。具体 Linux 系统/CPU 的原生工具包兼容范围由发布矩阵和实机验证确定，不声称任意旧 NAS 内核均支持。

## 2. 用户操作路径

### 原生媒体模式

1. 下载并解压已构建的离线包，双击 `栖库.exe`。
2. 首次用 Windows 原生目录对话框授权媒体根，可跳过并创建受控的空媒体目录；随后打开浏览器创建管理员和添加媒体库。
3. 首次设置完成后，后续双击自动复用配置并打开页面，不出现命令行窗口。重复双击唤醒已有实例。
4. 托盘提供打开媒体库、添加/管理授权目录、查看数据/日志、重启和退出；关闭浏览器仍继续运行。
5. 目录配置修改经校验后原子保存，首版采用受控重启生效，不在扫描和播放中随意改写运行配置。网络源暂不可达时提示离线，不把整库清空。

### Docker 全功能模式

1. 启动器检查已安装的 Docker Desktop、本机目标 context、Linux 容器模式及可用资源。
2. 缺少 Docker/WSL 时显示具体前置步骤，首次安装可能需管理员操作和重启；不承诺全新系统零确认一键。
3. 条件满足后由启动器自动生成本实例配置、拉取固定已发布镜像、启动 app/helper 并等待真实就绪。
4. qB/Jackett 初始化继续沿用现有用户主动点击与告知确认；Jackett 站点仍需用户配置，不把安装成功等同于已有可用搜索来源。
5. 关闭启动器与停止容器应在界面明确区分。停止全栈必须涵盖 helper 动态创建的本实例引擎，不能只执行 `compose down` 就宣称引擎已停止。

## 3. 原生进程与服务生命周期

- 新增 `cmd/nas-desktop/main_windows.go`、`internal/desktop/`；原 CLI `cmd/nas` 继续提供 NAS/开发入口。
- 数据锁抽象具有 Linux 文件租约与 Windows 文件/命名锁实现；Linux 标准信号退出、systemd/容器托管方式继续适用，不默认安装系统服务。
- 使用 Windows 原生托盘/目录选择/消息提示能力，优先复用 `x/sys/windows` 与封装良好的平台 API，不先引入 Electron、Tauri 或 Wails。
- 数据目录锁覆盖数据库打开、恢复任务、工作协程直到关闭；不能仅通过端口或 PID 文件判重。
- 启动器对同一用户/数据实例使用命名互斥量及限当前用户 ACL 的 IPC；IPC 仅开放固定动作，不执行任意命令，不将口令放入 URL。
- 原生默认监听 `127.0.0.1:8090`；端口冲突后在有限候选范围实际 bind，保留 listener 后再初始化后端，消除先探测再占用竞态；成功端口持久化。
- `/healthz` 通过且网页入口可服务后才打开浏览器；确认该地址对应本实例，不能把第三方占用的健康接口当作自己。
- `internal/app/server.go` 提供可复用 listener/生命周期选项，保留 `Run` 的兼容包装；真实绑定成功才输出已启动日志。
- 退出使用 context 取消、有序 HTTP/工作协程/媒体子进程关闭，超时给出中文诊断。原生退出不杀用户其他 qB/FFmpeg/Docker 进程。
- 支持日志轮转和受限自动重试，持续失败展示可操作原因，避免无限重启循环。

## 4. 资源、工具与配置

- 新增静态资源 FS 抽象及发布专用 `go:embed` 构建；release 脚本先构建网页、暂存资源再编译。开发无嵌入时继续使用 `NAS_WEB_DIR`，缺少资源使发布构建失败，不生成残缺包。
- Dockerfile 同步调整资源构建步骤，保留现有容器路径/部署兼容；阅读器动态 chunk、字体、图标均本地包含，断网可打开界面。
- 包内携带固定版本 `tools/ffmpeg.exe`、`tools/ffprobe.exe` 与许可证/来源/校验和。增加统一 resolver，所有探测、封面和诊断采用同一绝对路径，不改系统 PATH，不从当前工作目录误加载二进制。
- Linux 归档按 amd64/arm64 配套正确的 FFmpeg/ffprobe 产物并核对动态依赖和许可证；原 CLI/容器已有系统工具查找方式兼容保留，不能让 `.exe` 路径进入共享命令逻辑。
- 发布前按选定 FFmpeg 构建实际启用的组件核对许可证与再分发材料；不能笼统声称所有 FFmpeg 包均相同许可。
- 默认数据根为 `%LOCALAPPDATA%\Qiku\profiles\<实例ID>`，包含 SQLite、缓存、日志和原生私有配置，应用包升级不覆盖数据。可由本机原生设置选择其他本地可写数据盘。
- 本机配置存 JSON，提供中文字段说明与本机目录选择；配置优先级为显式启动参数 > NAS_* 环境变量 > 本地配置 > 默认。实际原 CLI 默认不因 desktop 配置而变化。
- 媒体根是目录数组，覆盖中文、空格、多盘符；新数据路径与媒体/下载区隔离。SQLite 必须位于本地磁盘，网络共享可作为显式授权媒体来源并独立验证访问身份。
- 原生默认回环访问；局域网共享为显式设置，在管理员初始化后开放并说明防火墙操作。原生目录授权只通过本机 UI，远端网页不能扩大宿主目录权限。
- 原生外接 BT/搜索沿用已有配置能力，但不作为本期 Windows 自动安装保证；单独验证路径映射、凭据私密性和发布门禁后才能宣称支持。

## 5. Windows Docker 全栈存储改造

现有 helper 的 Linux bind 模式继续保留。增加一个由可信部署配置选择的 `named-volume` 存储驱动；浏览器不能提交卷名、宿主路径或挂载 JSON。

- 以安装 ID 派生 app-data、helper-state、qB-config、Jackett-config、downloads、connections、IPC 等固定卷，支持同一下载卷同时挂载 qB rw 与 app ro。
- helper 在 Linux 卷内保持现有 UID/GID、私密权限、flock、原子清单和 `pwritev2` 预检；app/helper/qB/Jackett 保持同一 Linux Docker 环境与专用 bridge。
- Docker API 使用 volume 类型挂载，不把 Docker 内部 Mountpoint 当作宿主 bind 路径；检查卷名、标签、实例 ID、驱动、实际容器挂载及模板身份，未知卷/容器冲突不接管。
- 需要同步修改 `config.go`、`docker.go`、`files.go`、`service.go`、`templates.go`、恢复逻辑、备份说明和可执行契约，不只改 Compose。
- 避免依赖旧 Docker API 没有的卷子路径功能；通过明确的分卷布局实现私密数据隔离。
- 普通 Windows 媒体目录使用只读长格式 bind，校验 Desktop 的共享权限和实际容器可读性；引擎私有配置不落 Windows NTFS bind。
- 默认 BT 文件存 Docker Linux 数据盘，应用中可直接播放/入库；界面明确数据位置与虚拟磁盘容量。它不是普通 `E:\Downloads` 目录，不自动复制超大视频到 Windows。
- 原生命名数据与 Docker 数据不共用；默认不给出直接复制 SQLite 的跨平台迁移按钮。已有 Windows 原生库与 Linux 库的绝对媒体路径、下载历史及实例凭据都需要显式迁移设计。
- Windows 启动器仅连接明确选中的本机 Desktop context；不受意外 `DOCKER_HOST`/远程 context 影响，不默认开放 TCP 2375。
- 镜像仓库、版本与 digest 来自发布清单。支持用户已有镜像加速和经验证的镜像归档导入；阿里云加速地址按用户实际可用配置检测，不写死公共地址、不自动改 daemon 配置或跳过 digest 校验。
- 固定 project/installation ID 追踪资源，停止、卸载和失败恢复只操作本实例；保留数据卷为默认，不运行全局 prune。

## 7. 升级、迁移与恢复

- 初版只提供用户下载新包、退出旧版、替换程序再启动的可控升级。使用原固定数据位置；不在本期自动覆盖正在运行的 EXE。
- 升级前创建一致性 SQLite 快照并保留应用版本和配置；缓存可重建，数据库结构升级需要与旧版本对应快照一起回滚。
- 发现旧 `data/library.db` 时先提示导入来源，停止旧实例再复制/一致性备份；路径与当前系统匹配才接入，不能静默合并两个账号库。
- 不为启动器修改业务 schema；如需新增桌面偏好优先独立配置文件。既有用户/收藏/进度/下载状态保持。
- 原生卸载/删除程序包不默认清空应用数据，更不删除原媒体。Docker 模式明确数据库备份不覆盖 qB 恢复数据、helper 安装状态、连接密钥及下载文件。
- 导出诊断包脱敏凭据、Cookie、API Key 和私密 URL，并清楚提示仍可能含本机路径。

## 8. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| Linux amd64/arm64 与 Windows amd64 构建 | 同时成功，平台导入隔离；不将编译等同于 ARM64 实机通过 |
| Linux 无桌面、现有 CLI/环境配置与 Compose/bind 启动 | 不强制使用 GUI，不改变旧默认；五类内容、下载/搜种、重启恢复与信号停止无回退 |
| 干净 Windows 11 x64，普通用户，无 Go/Node/Docker/全局 FFmpeg | 解压双击原生媒体包成功，创建管理员，添加/扫描/打开五类内容 |
| 发布目录/用户名/媒体路径带中文、空格、多盘符；从任意工作目录启动 | 网页、工具及数据库定位正确；不会在随机目录创建第二份数据 |
| 断网启动、无默认浏览器、工具缺失或损坏、目录不可写 | 成功打开本地资源或明确可恢复错误；不静默闪退、不显示假就绪 |
| 连续/并发双击、同库 CLI 与桌面并发启动、端口被别的程序占用 | 一个写入实例，正确激活/拒绝；保留 listener、真实地址与实例身份 |
| 关闭网页、托盘退出、重启、扫描中退出、休眠唤醒 | 生命周期可解释，后台任务可恢复，无错误重复执行和残留子进程 |
| 网络媒体离线、权限变化、NTFS junction/大小写/边界路径 | 保留索引与进度，授权边界和发布门禁不被绕过 |
| 更新/备份恢复 | 用户、收藏、五类进度与库 ID 保留；版本不匹配拒绝危险回滚 |
| 超过 4 GiB 的字节偏移及真实大视频 | 保留鉴权 HEAD/Range/206/416；稀疏样本只证明协议，真实起播/拖动/内存另测 |
| Desktop 未安装、未启动、Windows 容器模式、非本机 context、虚拟化/WSL 不满足 | 给出准确前置步骤，不修改远端或其他项目、不谎报成功 |
| Desktop 可用且仓库可达 | 真实发布镜像、命名卷、app/helper/qB/Jackett 完整安装、认证、重启与状态恢复 |
| 镜像失败/断网重试、已存在未知资源、helper 重启 | 保持幂等与原凭据，显示真实进度，不接管未知资源 |
| 停止/卸载 Docker 实例 | 覆盖 helper 创建的本实例引擎；其他容器/镜像不受影响，数据默认保留 |
| Windows Docker 验证资源清理 | 专属标签、基线清单、精确清理并核实；不全局 prune |

实现后运行 Go 格式/构建/vet、Linux/Windows 构建矩阵、前端严格类型与生产构建、两端原有可复用集成验证和新的 Windows 交互验收；新临时单元测试执行后依用户要求清理。旧 Linux 服务器不能替代 Windows Desktop 验收，Windows 构建通过也不能替代 Linux 回归。本轮没有执行以上实施验收。

## 9. 扩展预留与不纳入首版事项

- 预留 profile/实例 ID、版本化配置和平台入口，支持后续 Windows ARM64/安装器。
- 开机启动、后台 Windows Service、无登录下载、自动更新、NTFS bind 托管下载和跨平台库迁移另列需求；不为一键启动重写媒体业务。
- 用户已于2026-11-18批准实施，P0–P3代码、发布/验证脚本和规范已落地；本地质量与行为证据见research，Docker部署仍由用户手动验收。P4未纳入本轮。
