# 插件系统、可配置市场与飞牛应用兼容改造计划

## Goal

为当前 NAS 内容管理系统规划插件系统、可配置插件市场和飞牛 OS 应用兼容能力；本次仅完成代码现状调研、兼容边界分析和分阶段修改计划，不实施业务代码。

补充用户于 2026-11-19 提出的 NAS 音视频获取方案推荐需求，核验 GitHub 上的候选工具，为后续插件候选和外部服务选型提供研究依据。

## 已确认的项目现状

- 用户希望增加插件系统，能够配置插件市场地址，并使用飞牛 OS 的插件。
- 项目使用 Go、SQLite、Vue 3 和 TypeScript，包含 Linux 容器部署与 Windows 原生桌面入口。
- 已有 qBittorrent / Jackett 引擎管理、可选助手和 Docker 集成，可作为插件生命周期设计的现有参考。
- 当前另有桌面图标任务处于 review，本任务单独建档，不修改既有任务成果。
- CodeGraph 与源码核实：现有执行助手只支持 Linux 两个固定引擎，主应用不持有 Docker socket；桌面完整模式严格核验服务、环境和卷，新增插件需同步修改验证器。
- 目前无通用插件模块，`GET /api/settings` 是只读回显，主库实际版本为 v2。

## 规划假设

- “飞牛插件”解释为飞牛 OS 应用包及应用中心中的第三方应用，而非现成的跨平台扩展 SDK。
- 同时考虑 Linux/NAS 与 Windows，能力受平台和部署方式约束。
- 推荐独立插件核心与市场协议，按实际宿主定义兼容层；不承诺任意 FPK 跨系统执行。
- 以下决策为建议方案，未视为用户已确认的实施范围；本轮仅规划。

## 待 P0 明确的输入

- 实际宿主和版本：本机 fnOS、普通 Linux、Windows，还是远程飞牛节点。
- 市场 URL、接口协议、认证和分发许可；不把任意网页 URL 当成标准市场源。
- 首批 3–5 个应用和版本，验证容器型、普通原生型和系统依赖型边界。
- 以上影响后续实施路线，不阻碍本轮完整计划交付。

## Requirements

### R1 插件核心

- 独立控制面管理来源、目录、不可变发布、兼容性、配置、授权和能力注册。
- 优先支持独立 Web 应用和外部服务；业务扩展经版本化类型协议或专用适配器接入。
- 执行与媒体服务解耦，插件不可用不阻塞已有媒体浏览和播放。

### R2 多市场

- 支持新增、编辑、测试、刷新、启停、移除，以及名称、协议、URL、优先级、刷新间隔和秘密引用。
- 首期实现可自托管的版本化 JSON 市场；飞牛或社区市场按实际协议分别适配。
- 不同市场同名应用不能自动合并或静默替换；停用或移除来源不停止已有安装。
- 后端有界拉取、可信签名、内容摘要、缓存和过期；内网源由显式策略允许。

### R3 执行与生命周期

- 新增可选执行助手，不扩大现有固定助手协议；主应用不持有 Docker 管理权限。
- 操作前生成锁定来源、版本、摘要、依赖、节点、权限及配置修订的计划，明确授权后执行。
- 安装、启停、升级和保数据卸载具有持久任务、幂等请求、资源归属、互斥和崩溃恢复。
- 权限扩大重新授权，数据升级不可逆时阻止自动降级，不承诺所有插件无损回滚。
- 执行端是实际资源和操作状态权威，主库期望安装记录不是接管证据。

### R4 飞牛兼容

- 分别声明市场读取、包解析和运行兼容，Docker 可用不代表完整飞牛环境。
- 真实 fnOS 宿主使用专用桥接与已确认原生管理机制，遵循权限、依赖、目录和向导语义。
- 只开放目标版本实测通过的动作；未验证升级、卸载等能力先不自动化，保留应用中心手工处理。
- 普通 Linux / Windows 只承诺经明确适配的容器应用及外部服务，不承诺任意原生 FPK。
- 远程节点另行设计身份、配对及认证，不开放任意 Docker / SSH 命令入口。

### R5 UI、存储与部署

- 新增插件中心、市场设置、详情 / 权限确认及真实进度，手机从“更多”进入。
- API 沿用会话认证、同源变更检查、严格 JSON、显式类型、中文错误与脱敏。
- 主库增量迁移保存市场、期望安装及授权；助手日志、秘密和插件数据独立持久化，明确备份边界。
- Windows Docker 模式同时调整 Compose、校验器、镜像清单、命名卷和完整停止协议；原生模式显示真实能力。

### R6 NAS 音视频获取选型补充（本轮仅调研）

- 根据用户请求检索 GitHub 官方仓库，比较影视/动漫自动订阅、网页音视频下载、音乐导入与自有远程文件同步的适用场景。
- 推荐中区分内容来源、索引器、下载器、整理工具和播放服务，说明各环节的必要前提。
- 优先考虑与现有 qBittorrent / Jackett 链路复用；用户未指定 NAS 系统和机型，先按常见 NAS 容器部署给出建议，宿主兼容性不视为已实测。
- 候选项目的外部事实、官方链接、核验日期和维护状态依据写入独立研究文件；PRD 仅建立研究引用。
- 本次不安装或部署候选工具，不视为确认首批插件清单，也不启动业务代码实施。

## Technical Approach

技术设计、字段解释、API、数据归属、文件与验收统一见 [info.md](info.md)。

顺序：P0 兼容验证 → P1 市场与插件中心 → P2 受控插件执行 → P3 飞牛桥接 → P4 完整生命周期与 Windows 集成 → P5 业务能力扩展及固定引擎渐进迁移。

P0–P2 是插件基础 MVP。若目标包含实际运行飞牛应用，P3 必须纳入首轮产品验收，不能用普通 Docker 成功替代飞牛兼容成功。

## Decision (ADR-lite，建议)

**背景**：当前跨平台核心和固定引擎能力与飞牛宿主框架存在边界；市场地址与应用执行属于不同层次。

**A：插件核心 + 真实飞牛桥接**。fnOS 为主要宿主时推荐，原生兼容性好，但要求真实飞牛与受信任宿主代理。

**B：自有跨平台插件市场 + 逐应用容器适配**。普通 Linux / Windows 为主时推荐，边界可控，但需要维护兼容模板，不能覆盖全部 FPK。

**C：通用 FPK 仿真层**。需复刻系统目录、权限、服务、API、向导与升级语义，成本和兼容风险高，首期不采纳。

**建议**：A / B 共享目录和控制面，按实际宿主选执行适配器。qB / Jackett 先走原路径，基础稳定后再显式迁移。

**后果**：市场和受控插件可独立交付，原生兼容受目标版本及应用验证约束，不宣称全生态跨平台支持。

## Out of Scope

- 本次不安装插件、不执行第三方安装脚本、不改动现有运行配置、不连接真实用户市场凭据。
- 不承诺任意飞牛应用在 Windows、普通 Linux 或受限容器内直接运行。
- 不复刻飞牛 OS、私有签名和审核体系，不绕过权限、认证或分发许可。
- 首期不支持任意脚本、任意 Compose / Docker 参数、前端代码注入或插件直连主库。
- 将本系统打成 FPK 是另一个分发需求，不是运行飞牛应用生态的验收结果。
