# 插件系统、多市场与飞牛应用兼容技术修改计划

> 日期：2026-11-19。状态：方案草案，可用于拆分实施；本轮不实施业务代码。
> 默认同时考虑 Linux/NAS、Windows 原生和 Windows Docker Desktop。用户尚未指定目标市场 URL、飞牛版本或首批应用，相关能力必须经样本验证。

## 1. 推荐结论

采用“插件控制面 + 可配置市场适配器 + 可选执行助手 + 按平台划分的运行适配器”。

- 第一条交付线：自有版本化市场协议、受审核的容器型插件、已安装管理及外部服务接入。
- 第二条交付线：真实 fnOS 主机上的原生应用管理桥接，复用飞牛自身应用管理能力。
- 飞牛 FPK 的元数据读取、市场展示和实际运行分别判断；成功下载或解析 FPK 不等于兼容运行。
- 普通 Linux / Windows 不承诺任意 FPK 直接执行。可移植容器型应用以明确模板重新适配；需要飞牛宿主 API、账户、目录和权限体系的应用保留在 fnOS 运行。
- 首期不把远程页面的 JavaScript 注入主应用，不使用进程内动态库作为默认扩展方式。

飞牛官方资料与证据以 [fnos-compatibility.md](research/fnos-compatibility.md) 为准；代码现状和行号见 [repository-impact.md](research/repository-impact.md)。

## 2. 当前系统与改造边界

当前为 Go HTTP 服务、SQLite schema v2、Vue 3 / TypeScript，已有媒体、下载、搜种、Linux 容器及 Windows 桌面两种模式。

已有引擎助手是两个固定组件的受信任部署设施：qBittorrent 和 Jackett 的镜像摘要、挂载、端口、身份与操作均受限。它使用独立状态库、私有 Unix socket 和持久任务。其 scratch 镜像也不具备运行 FPK 安装脚本的通用 shell 环境。

应复用类型化接口、认证门面、幂等任务、持久意图、资源归属核验与恢复方式；不直接把现有组件参数改成任意 URL、镜像、Compose 或命令。

`GET /api/settings` 当前是只读配置回显。因此“网页可配置市场地址”需要新增持久化记录和 CRUD 接口，仅增加启动环境变量无法满足需求。

## 3. 架构与职责

```text
Vue 插件中心 / 市场设置 / 安装确认
                  |
                  v
主应用认证 API -> 插件控制面 -> 市场适配器 -> 自有市场 / 已验证的社区源
                  |
                  +-> 兼容性判定 / 权限计划 / 插件能力注册
                  |
                  v
         私有插件执行接口
                  |
       +----------+----------------+
       |                           |
可选 Docker 插件助手          可选 fnOS 宿主桥接
       |                           |
受审核声明式容器模板       飞牛自身应用生命周期工具
```

### 3.1 控制面

- 管理市场、规范化目录、来源身份、版本、兼容性、用户配置和授权。
- 先生成不可变安装计划，再提交执行；浏览器只提交计划 ID、请求 ID 和版本修订号。
- 管理插件提供的能力类型，例如下载器、搜索源、元数据服务或独立 Web 应用。
- 先支持 `web-app` 和 `external-service`；业务能力扩展仅经显式类型化适配器注册，不开放任意主程序函数调用。
- 第三方服务通过版本化 HTTP/JSON 能力协议或专用适配器交互；核心通过有限能力接口取数据，不授予主数据库直连或任意文件访问。

### 3.2 市场适配器

- 首期提供 `qiku-index-v1`：可自托管的静态 HTTPS JSON 目录、发布元数据与包下载位置。
- 每种第三方市场单独实现解析器，配置 `kind + url`；新增 URL 不会自动获得未知协议解析能力。
- 飞牛官方市场与社区市场分别建模，不把第三方自称“飞牛市场”当成官方协议。
- 未验证可公开使用的目录协议时，先支持受控 FPK 元数据导入 / 人工整理的兼容目录；第三方在线源接入列为独立验收项。

### 3.3 执行助手与运行适配器

- 新增独立 `nas-plugin-helper`，保留现有引擎助手的固定协议；两个执行面使用不同安装命名空间、状态目录、私有 socket 和资源标签。
- Docker 适配器只接收已核验、已授权的声明式部署计划，不提供任意 shell / Compose / 原始 Docker JSON 执行端点。
- fnOS 适配器部署在真实飞牛宿主，执行已验证的固定应用管理操作；主应用容器内存在 Linux 内核或 Docker 并不能证明飞牛管理工具可用。
- 外部服务适配器只探测和连接，不宣称拥有服务安装或卸载权限。
- 后续若支持远程 fnOS，增加节点身份绑定、双向认证和独立配对流程，不能通过放宽现有 Docker Desktop 本地上下文检查来实现。
- 插件助手持有 Docker 或宿主管理权限，属于高信任组件；接口白名单不等于 Docker daemon 权限沙箱。

### 3.4 部署能力矩阵（目标设计）

| 部署方式 | 市场 / 配置 | 经适配容器应用 | 飞牛原生 FPK |
| --- | --- | --- | --- |
| 真实 fnOS 宿主 + 已授权桥接 | 支持 | Docker 可用且满足清单条件时支持 | 仅开放经目标版本验证的原生管理操作 |
| 普通 Linux + Docker + 插件助手 | 支持 | 经审核模板和权限验证后支持 | 不承诺原生运行，只能逐项移植或连接飞牛节点 |
| Windows Docker Desktop Linux 模式 | 支持 | 完成发布、卷、验证器与停止协议改造后支持 | 不在 Docker Desktop 中模拟整个飞牛宿主 |
| Windows 原生，无 Docker / 飞牛节点 | 支持 | 本地安装能力不可用，可接外部服务 | 本地执行不可用；远程桥接属于后续独立能力 |

架构和宿主检测来自实际执行节点，而不是网页浏览器所在电脑。CPU、系统版本、依赖和权限仍需逐插件匹配。

### 3.5 飞牛原生操作的已知边界

官方所查 `appcenter-cli` 文档列出 `install-fpk`、`list`、`start`、`stop`；本轮未从该页证实稳定的升级、卸载、取消、结构化输出或异步进度接口。这些能力统一进入 P0：锁定目标系统版本，读取实机帮助，验证命令权限、输出、退出码、向导及失败恢复后再开放。包内存在升级 / 卸载生命周期钩子，不等于对外管理 CLI 已有对应稳定命令。

`install-local` 属于开发安装，不向市场用户开放；不得为某插件静默调用 `default-volume` 修改宿主全局安装空间。需要向导环境文件时由桥接生成私密临时文件，敏感值不进命令行或日志。

官方文档未在本轮覆盖页面中给出通用第三方市场订阅协议；这只是所查范围的未证实项，不能断言其他合作接口不存在。FPK 的确切归档、压缩和签名层次也不在当前已确认契约内，自行解析之前先验证真实样本，不写死为某种压缩格式。

## 4. 多市场地址与信任模型

### 4.1 市场配置项

| 字段 | 中文说明 |
| --- | --- |
| `id` | 本地生成的稳定来源编号，修改名称或地址不会改变已有安装身份 |
| `name` | 管理员可读的市场名称 |
| `kind` | 已知市场协议类型；首期只承诺自有协议，其他类型经适配后开放 |
| `url` | 目录入口地址；普通网页地址不一定是可解析的市场接口 |
| `enabled` | 是否参与目录刷新；停用不停止或卸载已安装插件 |
| `priority` | 目录展示及用户显式允许时的解析顺序，不允许静默替换同名插件 |
| `refreshIntervalMinutes` | 自动刷新间隔，受全局最小间隔与并发预算约束 |
| `credentialRef` | 后端私密凭据引用；API、日志和普通备份不包含凭据内容 |
| `trustKeyFingerprint` | 经管理员确认的市场签名公钥指纹；密钥轮换需显式信任流程 |
| `networkPolicyRef` | 允许访问的域名、端口和内网范围策略引用 |
| `lastSuccessfulRevision` | 最近成功核验的目录版本，用于缓存、过期和回退保护 |

支持添加、修改、连接测试、刷新、启停和移除；测试和刷新均无安装副作用。修改入口、认证或信任密钥需要重新校验，不把旧来源身份静默映射到新发行者。

### 4.2 索引与插件清单

市场索引包含 `schemaVersion`（协议版本）、`revision`（目录修订）、`expiresAt`（有效期）、`plugins`（发布列表）、`signature`（签名）。每个可安装发布至少提供：

- `publisher`、`id`、`version`：发行者、插件和版本身份；显示主键为 `marketId/publisher/pluginId`。
- `runtime`、`os`、`arch`：运行方式、支持系统与处理器架构。
- `minHostVersion`、`apiVersion`：最低主程序版本与能力协议版本。
- `artifact`、`sha256` / `imageDigest`：包位置及不可变内容标识；不能只锁定可变 tag。
- `permissions`、`configSchema`：声明权限与受限配置表单，不允许脚本式 UI。
- `dependencies`、`conflicts`：依赖及冲突约束，安装前解析并拒绝循环或不可满足依赖。
- `healthcheck`、`entrypoints`：受限就绪检查与可访问入口。
- `dataSchemaVersion`、`rollbackPolicy`：数据兼容与可回退条件；没有声明不代表可自动降级。

安装计划锁定来源身份、目录修订、发布摘要、依赖图、运行节点、权限集合和配置修订；过期或被改动的计划不可继续执行。

### 4.3 网络与内容边界

- 后端获取目录，限制响应大小、耗时、重试、并发、重定向次数及缓存容量；失败保留最近成功目录并标记过期，不能把故障视为空市场。
- 默认 HTTPS。自建内网市场通过部署级精确策略显式放行，逐次校验 DNS、连接目标和重定向，阻止访问 metadata、回环或未授权网段。
- 认证不能随跨域跳转泄露；目录下载、包、图标和健康探测各自遵守对应网络策略。
- 校验摘要与可信签名。哈希只证明内容一致，不能单独证明发行者可信；不能从同一未信任目录自动建立信任根。
- 离线缓存可以展示，过期或签名无效的目录不能发起新安装；已安装插件保留独立锁定元数据。
- FPK / 其他压缩包执行有界解析：限制压缩与展开总量、文件数、单文件大小、路径深度；拒绝目录穿越、逃逸软链接、设备文件等。

## 5. 数据、任务与生命周期

### 5.1 数据分工

- 主库增量迁移 v2 → v3，新增市场、发布锁定记录、期望安装、权限授权及操作绑定。不得重建或改写现有媒体/账户/下载表。
- 实施前重新核实当时实际 schema 版本；若其他任务已先占用 v3，则使用下一个增量版本，不能覆盖其他迁移。
- 发布索引缓存可以放独立缓存目录，主库保留必要来源与安装锁定元数据。
- 插件执行助手独占自身 SQLite 状态库，保存资源所有权、实际安装身份、执行步骤、事件与恢复意图；秘密保存在权限受限私密文件中。
- 主应用中的安装记录是控制面配置和观察结果，不是接管容器或宿主应用的所有权证据；执行端是效果、资源身份和任务状态的权威。
- 插件的独立数据卷与已有媒体、主数据库、下载 staging/complete、引擎连接和秘密目录隔离。

### 5.2 操作模型

安装：解析兼容性 → 锁定版本和依赖 → 展示权限 → 明确授权 → 持久化意图 → 下载 / 拉取 → 核验 → 准备资源 → 启动 → 健康检查 → 注册能力。

升级：预检数据兼容与备份能力 → 保留旧发布和配置 → 准备新版本 → 受控停止 / 切换 → 验证就绪 → 确认提交。失败时只在数据契约允许时回退，否则进入明确的人工恢复状态，不能承诺任意插件一键无损回滚。

卸载：停止并撤销能力 → 核验所属资源 → 移除程序资源 → 默认保留数据。删除业务数据必须是另一个显式确认动作；不得删除外部应用或未知目录。

- `requestId` 幂等绑定不可变计划；同 ID 改参数返回冲突。
- 每个实例/依赖集合加互斥，更新检查 `revision`；重启从持久意图对账，不盲目重复创建资源。
- 分开记录安装状态、运行状态和就绪状态。任务阶段支持 `queued/running/succeeded/failed/cancelled/recovery_required`；不支持安全取消的阶段应明确拒绝取消。
- 市场移除、刷新失败或控制面退出不自动卸载插件。
- 宿主原生应用由 fnOS 管理生命周期；退出本系统不隐式停止其他飞牛应用。项目独占插件容器的完整停止策略单独定义并接入桌面退出协议。
- 升级后权限扩大必须重新授权；不自动接管现有 qB/Jackett。迁移现有引擎安排在插件基础稳定之后，沿用旧 API、连接、下载选集和发布门禁。

## 6. API 与前端修改

建议 API 分组（实际路径随契约评审固定）：

| API | 作用 |
| --- | --- |
| `GET /api/plugins/capabilities` | 返回当前平台、节点、运行方式及可执行能力，附不可用原因 |
| `GET/POST /api/plugin-markets` | 查询 / 新建市场 |
| `PATCH/DELETE /api/plugin-markets/{id}` | 修改 / 移除市场元数据，已安装项目保留来源快照 |
| `POST /api/plugin-markets/{id}/test` | 测试访问、协议和签名，无安装副作用 |
| `POST /api/plugin-markets/{id}/refresh` | 有界刷新与更新缓存，无安装副作用 |
| `GET /api/plugins/catalog` | 按来源、类型和兼容性查询规范化目录 |
| `GET /api/plugins/installations` | 查看已安装项目、归属、配置和状态 |
| `POST /api/plugins/install-plans` | 计算并锁定安装 / 升级 / 卸载影响及权限 |
| `POST /api/plugins/installations` | 执行已授权安装计划，返回持久操作编号 |
| `POST /api/plugins/installations/{id}/actions` | 对已拥有资源执行允许的启动 / 停止 / 升级 / 卸载动作 |
| `GET /api/plugins/operations/{id}?afterSequence=...` | 有界读取真实阶段、事件与恢复状态 |

所有接口沿用登录鉴权、同源变更检查、严格 JSON、中文错误与敏感信息脱敏；不扩大现有全局请求体预算。未来包上传须单独流式限额。

前端新增“插件中心”：市场、已安装、操作记录三个视图，市场设置支持多地址和来源协议。详情显示发行者、原始来源、摘要、运行方式、架构、权限、数据目录、兼容理由与升级差异。安装前展示不可变计划；权限不预勾选。

复用现有懒加载、单一原生弹窗、焦点恢复、单请求轮询、取消与旧响应隔离。新增 `ViewName` 管理视图而非 `ContentType` 媒体类型；手机仍从“更多”进入。

独立 Web 应用首期通过经过校验的独立来源链接打开，不共享主应用会话。后续内嵌需单独设计独立 origin、CSP、Cookie 和权限隔离，不直接运行市场提供的任意前端代码。

## 8. 分阶段实施与出口条件

| 阶段 | 工作内容 | 可验收交付物 / 出口条件 |
| --- | --- | --- |
| P0 兼容验证与协议定稿 | 明确目标宿主、版本、市场协议和 3–5 个目标应用；检查 FPK 类型及所需权限；在隔离真实 fnOS 节点确认管理能力 | 兼容矩阵、市场样本、自有清单 v1、允许操作表、不可支持原因；未验证的升级 / 卸载等操作不可开放 |
| P1 市场与插件中心 | 数据迁移、多市场 CRUD、测试 / 刷新、签名与缓存、目录查询、兼容性展示 | 可配置自建目录并查看多市场，故障保留缓存，无 Docker / FPK 安装副作用 |
| P2 第一版插件运行 | 独立助手、受审核容器 / 外部服务适配、安装计划、启动 / 停止、健康检查和日志 | 完成至少一个真实受控插件的安装到就绪链路；稳定幂等、资源归属核验与中断恢复；现有引擎保持原路径 |
| P3 飞牛原生桥接 | 在真实 fnOS 宿主部署桥接，使用经过 P0 证明的原生操作接入应用；社区源按已确认协议适配 | 分别验证容器型、普通原生型和系统依赖型样本；明确支持 / 限制 / 不支持，保持飞牛权限和数据目录语义 |
| P4 生命周期完整性与跨平台 | 自有插件升级 / 保数据卸载 / 受限回退；Windows Docker 校验、发布、停止协议；必要的备份导出 | 旧版本保留、失败恢复不误删数据；整机退出后本实例资源符合策略；原生 Windows 对不支持操作有明确原因 |
| P5 业务扩展与逐步迁移 | 根据真实需求增加元数据、下载、搜索等能力适配；显式迁移固定引擎的所有权与配置 | 旧接口与下载发布门禁不变；禁用插件不损坏核心媒体功能；文档和可复用集成验收脚本齐全 |

P0、P1、P2构成推荐基础 MVP；若业务成功标准是“真实使用飞牛应用”，必须把 P3 纳入首轮产品交付，不能用普通 Docker 插件运行成功替代飞牛兼容验收。无 fnOS 主机时，首版承诺限制为自有插件及经过明确适配的容器应用。

P4 的安全数据语义在 P0/P2 就必须定义；阶段后移的是完整升级/卸载功能，而非先实现不受保护的执行入口。
