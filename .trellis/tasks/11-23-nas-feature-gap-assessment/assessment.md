# 栖库 NAS 内容管理系统功能缺口评估

评估日期：2026-11-23（Asia/Shanghai）  
评估基准：`main` / `6f380be`  
评估方式：已有 CodeGraph 索引 + 源码/API/模型/前端/契约/历史验收记录交叉检查。未启动服务、浏览器或真实 NAS；以下历史测试结果不代表本轮重新执行。

## 1. 判断

当前系统已经超出“媒体浏览器原型”：五类媒体、进度、搜种下载、RSS 与自动规则、网页获取、本地/远程导入、四类外部自动化 API 和固定组件部署都有实际实现。

**下一阶段最需要补齐的是：作品化管理、从入库到可播放的兼容体验、账号与恢复能力，以及无人值守运行时的异常与容量治理。** 再增加获取来源的收益，暂时低于让已经取得的内容更好找、能播放、可维护。

本报告默认面向个人/家庭局域网 NAS。若定位多用户公网服务，账户授权与访问安全需要前置；若主要听音乐，迷你播放器/队列需要前置。这些是优先级调整条件，不是本轮已确认的新开发范围。

## 2. 已有基础，避免重复建设

| 领域 | 已实现能力 | 当前边界 |
| --- | --- | --- |
| 媒体库 | 视频、图片、漫画、小说、音乐；扫描、封面、分页、标签、收藏、继续消费 | 主要是文件级内容模型 |
| 播放与阅读 | 鉴权 GET/HEAD/Range 原文件流；漫画多模式、TXT/EPUB 目录与设置、服务端进度 | 取决于浏览器解码；同一账号跨设备恢复已有基础 |
| 下载与搜索 | qB 添加、选文件、启停、限速、对账、入库重试；Torznab 搜索 | 不把“搜索成功/下载100%”当入库成功 |
| 资源收集 | RSS、自动规则、网页视频/音频、本地登记/复制、预配置远程复制 | 原生流程已有获取→发布→扫描→核验真实条目 |
| 外部工具 | MoviePilot、AutoBangumi、Sonarr/Radarr API；MoviePilot 六阶段工作流 | 外部整理/刮削存在，但不等于本地媒体详情已经作品化 |
| 组件部署 | 四个固定组件的受控部署、启动、进度、任务恢复与失败重试 | 固定白名单，不是通用插件市场；停止完整模式另有实现 |
| 基础可靠性 | 持久任务、取消/重试、挂载失联保护、只读源文件、空间预算、数据库一致性快照 | 全量恢复与目标 NAS 实测仍有缺口 |
| 基础安全 | bcrypt、随机会话摘要、HttpOnly/SameSite Cookie、同源变更校验、路径隔离 | 只有一个管理员，账号生命周期管理不足 |

证据详见三个研究附件；尤其不能把“完全没有刮削”“没有订阅”“没有导入”“没有备份”“没有跨设备进度”作为当前整体结论。

### 几个需要准确表述的边界

- **改名后的状态关联是结构风险推断**：由路径唯一键和 item_id 外键推得，尚未隔离复现；不能直接宣称当前必然丢进度。
- **搜索并非必须马上换技术栈**：先补筛选与批量管理，有真实大库基准后再决定全文索引；目前未测出具体性能瓶颈。
- **浏览器原生菜单因设备而异**：这里只判断应用缺统一字幕/音轨/外部播放集成，不把原生速度、画中画或投屏一概说成不可用。
- **外部刮削已存在**：缺的是把本地 NFO/作品关系转换为栖库可管理的结构，而非再做一套外部刮削按钮。
- **日志与局部操作记录已存在**：缺的是统一事件、离线通知及必要的管理审计；不是完全没有审计。
- **不建议默认扩写媒体源文件**：元数据覆盖优先存主库或独立衍生区，原媒体只读边界继续保留。

## 4. 单列的发布验收缺口

这些是尚缺的证据，不是功能不存在，也不是本轮发现运行故障：

1. **真实目标NAS和Docker部署**：四产品真实镜像首次初始化、UID/ACL、Linux挂载、Docker Desktop卷与组件连接。见 `docs/verification.md:405-417`。
2. **真实大库/大媒体性能**：真实影片起播、拖动、并发播放+扫描/下载、峰值CPU/内存/磁盘，以及大量条目的查询延迟。稀疏5GiB Range不证明这些。见 `docs/verification.md:73,239,255`。
3. **完整恢复演练**：主库、来源秘密、helper身份、worker状态及组件/下载数据一致恢复，断电/失联后不重复提交未知外部写操作。见 `docs/collection.md:121-123`、`docs/components.md:56`。
4. **真实来源兼容**：本地协议fixture通过不能替代真实云盘、公网站点和真实第三方服务运行。MoviePilot能力还受当前已核验版本限制。见 `docs/verification.md:373,393,417`。

`collection-file-import` 和 `collection-release` 的 in_progress 主要包含这些目标环境验收，不能仅凭任务状态把其功能列为未做。旧插件PRD记录的v2/两引擎也是历史上下文，当前不能照搬。

## 5. 建议迭代顺序

### 第一批：能持续使用、能恢复

- 管理员改密/受控重置/全部会话撤销。
- 定时备份、备份校验，将现有恢复材料说明落实为可核对的备份清单，先支持停机检查/恢复。
- 最小事件中心：失败、待确认、磁盘/备份风险；明确能在哪里处理。
- 并行补目标NAS实机验收与恢复演练，不把未验事项永久留在review。

**出口**：用户不需查数据库就能管理凭据；关掉网页也能发现关键异常；一套隔离实例能按清单恢复并保留账号、收藏、标签和进度，外部不确定操作不会重发。

### 第二批：内容管理与可消费性

- 先电影/剧集作品模型与本地NFO/封面、人工纠错，明确文件与作品关系。
- 加入外挂字幕、媒体轨道/编码诊断；根据目标设备结果选择转封装/音频转码。
- 加入未看/已看与多标签筛选、批量管理；失联条目提供显式重新关联。

**出口**：一部剧以作品/季集浏览；已有刮削资料可在本库使用；重扫不覆盖人工纠错；字幕可选且关闭可回收资源；不兼容影片给出明确原因和可执行处理方式。

### 第三批：无人值守和长时间运行

- 将外部成品目录接入显式授权的自动发现/导入；展示从来源到真实本库条目的链路。
- 做任务/产物占用可视化、保数据归档和受控暂存清理。
- 补规则模板、缺集视图及组件维护/版本兼容，再考虑受控升级。

**出口**：常用来源一次配置后能追踪到本库条目；异常自动转人工且有通知；历史增长有明确维护路径，不靠停机手工改库。

### 第四批：按主场景选择扩展

音乐优先则做全局播放器/专辑/歌单；家庭优先则做多用户权限；照片/阅读优先则做时间线/书签。通用插件/飞牛兼容、电视客户端和更广格式作为独立后续范围，避免同时扩成多个不完整子产品。
