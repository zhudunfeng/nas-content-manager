# NAS 内容管理系统分阶段实施计划

## Goal

依据已完成的功能缺口评估，将推荐方向转化为有依赖、可独立实施、可验收和可恢复的 Trellis 任务。本轮交付实施计划与子任务，不实施业务功能。

## 已确认输入

- 用户要求“请按推荐制定逐步可实施的计划”，沿用上一轮评估建议的次序。
- 基准为 main / `6f380be`，业务源码未变化；已有评估资料保留，不覆盖。
- 当前代码具备五类媒体、获取/发布/入库、四外部组件控制和部署基础。
- 复用 Go/SQLite/Vue 与既有任务、只读媒体边界、私密执行端和增量迁移机制。

## 规划默认

- 以个人/家庭局域网 NAS 为主；首轮继续单管理员，家庭多用户作为后续分支。
- 必做顺序：运行基线 → 账号/备份/事件 → 作品/元数据/字幕/管理 → 外部导入/容量/规则/组件维护。
- 以可验收的任务和小 PR 为单位，不在缺少团队产能与目标设备信息时承诺日期。
- 真实 NAS 验收可以与开发分轨推进；设备缺失阻止宣称通过，不阻止独立代码任务规划。

## Requirements

- 建立总路线、依赖关系、里程碑、工作量相对级别、推荐下一任务和后续可选方向。
- 为核心范围建立子任务，每个包含目标、明确范围、不做事项、拆分顺序、入口文件与验收。
- 跨层变更给出拟议 API/数据/生命周期和迁移策略；实施前按实际头版本复核，不把设计写成现有能力。
- 将功能验收、本机受控验证、目标环境实测分开，沿用临时单测清理与集成脚本保留约束。
- 保留现有数据、只读媒体、鉴权和发布门禁；不盲重发不确定外部写操作。

## Acceptance Criteria

- [x] 总路线和核心任务依赖完整，区分整项与切片前置，依赖无环并消除隐含互等。
- [x] 十二个核心子任务均有可执行范围、小交付顺序、验收与回退边界。
- [x] 第一项任务不需要再次做功能缺口评估即可开始；目标设备输入列为验收前置。
- [x] 核心API/模型/恢复/安全边界有拟议契约，原契约保持真实现状。
- [x] 只新增本计划及其子任务文件，不修改业务或已有任务资料。
- [x] 文档、JSON/JSONL、链接、上下文、任务父子关系和引用经过定向语义及结构复核。

## Definition of Done

- 规划资料与研究落盘，保留 planning 状态代表尚未实施。
- 本轮不启动业务、Docker或真实组件，不生成单元测试。
- 已评估 code-spec：新设计保存在计划，实施任务逐步把确认并实现的契约写入对应 spec。

## Out of Scope

本轮业务实施、真实数据迁移、部署、正式发布；首轮硬件视频转码、任意插件/FPK运行、多用户、公网身份联邦、全功能音乐/照片/阅读平台。

## Decision（规划取舍）

采用“先恢复能力、再内容管理、再长期自动化”的增量路线；基础字幕/筛选/只读容量/模板可在技术依赖满足时提前。另两条可行路径是以音乐/家庭成员等主场景提前分支，或先做更广的插件/转码平台；当前没有相应新增主场景输入，故将它们保留为明确触发条件的后续分支。这样可逐项验收，代价是首轮不覆盖所有终端和格式。

## 实施交接

- 已建立12个子任务，推荐从S01开始，随后S02；本轮不自动进入业务实施。
- 元数据/字幕sidecar发布授权、用户原始素材恢复、账号并发撤销、worker冷热幂等、组件安装身份兼容为实施阻断检查点。
- 新模型/API/预算均为拟议；实际实现后再分任务更新spec。本轮不把未实现契约提前写入正式规范。
- 所有任务保持planning，`.current-task`保留父规划；目标NAS/真实组件/实际接收端输入在对应步骤前补，不虚构本轮实测。

## 规划复核与验证

- [定向语义复核](research/quality-review.md)已完成，相关修正同步父/子PRD与研究；没有剩余规划阻断问题。

- 规划交付完成，功能任务仍为planning；按总路线从S01进入后续实施。
