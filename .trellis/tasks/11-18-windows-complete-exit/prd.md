# Windows 本地完整退出与文件释放

## Goal

修复 Windows 本地桌面启动后点击「退出」仍有进程存活、文件未释放的问题，使本应用拥有的服务、工作进程、监听和资源有序关闭，并可立即重新启动或更新程序。

用户补充：文件占用验收**优先针对构建后的程序本身**，尤其主 EXE、应用启动的工具程序/依赖及程序目录能否立即覆盖、替换、重命名或删除；数据库和媒体文件释放是补充回归，不应取代程序更新验收。

## Requirements

- 追踪原生窗口/托盘退出、IPC 退出与共享应用生命周期，先复现和定位，再实施最小可靠修复。
- 「退出」关闭本应用拥有的进程、后台任务和媒体工具子进程，等待资源实际释放，覆盖 SQLite、媒体文件、日志、监听、单实例锁与命名管道；不误杀系统浏览器或其他独立实例。
- 首要检查退出后构建产物 EXE 的零共享读写、原位覆盖及程序目录重命名；覆盖后立即重启，证明用户能够重新构建或换包。工具进程应验证其映像文件解除占用；没有实际执行的第三方 DLL 不得宣称已实测。
- 保持原有关闭窗口、单实例唤醒、重启和 Windows/Linux 兼容契约；Docker 既有运行策略不得擅自扩大为删除外部资源。
- 处理后台任务执行中、长连接/媒体流、重复退出和退出失败等边界，避免假成功、无期限阻塞或只隐藏窗口。
- 新增方法/字段/配置和关键业务逻辑使用中文说明、明确类型及中文日志。
- 构建与验证使用项目内 `.runtime/` 环境；仅操作本轮隔离实例，不运行 Docker、不操作真实媒体或凭据。新增临时测试源验证后删除。

## Acceptance Criteria

- [x] 根因有可审阅证据，退出相关入口共用一致的生命周期。
- [x] Windows 实际退出操作后，隔离主进程及其应用拥有的子进程结束，HTTP/IPC 不再监听。
- [x] 隔离数据库、日志、媒体与程序文件可独占打开/重命名，单实例资源释放，退出后能重新启动。
- [x] 构建后主 EXE 在进程退出后立即可覆盖，整个隔离程序目录可重命名/恢复，覆盖后的 EXE 可立即启动；自有工具映像解除占用。
- [x] 活跃任务/连接、重复退出、关闭窗口与外部资源保留有针对性验证。
- [x] gofmt、vet、适用测试/构建通过，Linux 兼容有对应证据；文档/规格同步，临时测试源清除。

验收采用真实 Windows 进程、命名管道、原生托盘消息泵与产品菜单派发；物理鼠标点击托盘和完整包第三方共享 DLL 留待目标机人工确认，Linux 仅交叉构建。最终桌面慢流/空闲退出 0.775/0.336 秒，EXE 原位覆盖、完整目录重命名及覆盖后重启通过；五媒体 52 项、下载 36 项、搜种 43 项、托管接入 35 项通过。详情见 `research/integration-validation.md`、`implementation.md` 和 `quality-review.md`。

三个临时 Go 测试源已清除。隔离应用进程为 0，但 `.runtime/windows-exit/verify` 样本目录的递归删除被自动审批策略阻止，仍保留本轮测试数据/凭据；未换用其他方式重试。Race detector 因本机缺 GCC 未完成，没有运行 Docker。代码待用户审阅，未提交、未归档。

## Technical Approach

先检查 `internal/desktop/` 与 `internal/app/` 资源所有权，再选择有界、可等待且可复用的关闭流程。实现和测试边界记录在 `research/` 中。用户已明确授权修复，按现有产品行为推进，不额外增加交互确认。

## Out of Scope

改版界面、安装器、全局进程清理、强制关闭用户浏览器、删除外部 Docker 资源、C 盘缓存清理。
