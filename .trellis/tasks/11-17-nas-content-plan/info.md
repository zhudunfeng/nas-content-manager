# NAS 内容管理系统技术设计

## 设计目标

实现易使用、易部署、界面美观的统一内容管理系统，内容覆盖视频、图片、漫画、小说。用户已批准按计划实施，首版边界以 prd.md 的 Approved implementation scope 和 docs/api.md 为准。默认面向一台支持容器的 NAS、个人或家庭用户；容量与性能待实际设备验证。

## 首版实现对照（2026-11-17）

- 技术选择已确定：Vue 3 + TypeScript + Vite、自有语义样式与 SVG 图标、Go 标准 net/http、modernc 纯 Go SQLite。未引入 Gin 或额外组件库。
- 首版数据库使用 users/sessions/libraries/items/user_items/progress/jobs，内容文件和基础元数据聚合在 items；下文独立 MediaFile、系列与多用户权限是未来扩展模型。
- 已实现四类列表与阅读、管理员会话、目录浏览、任务持久化、Range 直放、标签收藏、进度、一致性备份及离线恢复。图片时间线、漫画系列聚合、书签、HLS 与转码不在本次交付。
- 单镜像/Compose 文件已交付，Linux amd64/arm64 二进制已交叉编译；目标架构容器运行与真实 NAS 性能尚待实测。
- 实际契约和验收记录以 README、docs/api.md、docs/verification.md 及 .trellis/spec/{frontend,backend} 为准。

## 推荐形态

- 一个应用镜像：编译后的 Web 页面、API、持久化任务调度和后台任务执行器统一发布。
- 一个 Compose 服务：默认不依赖 PostgreSQL、Redis、Elasticsearch、对象存储或独立反向代理。
- 一个业务数据目录：保存配置、SQLite 数据库、备份与衍生缓存；备份时区分不可丢失数据与可重建缓存。
- 一个内容入口：四类内容有专用页面，共用登录、媒体库、搜索、标签、收藏、最近访问与任务通知。
- 多个只读媒体目录：默认纳管已有文件，不搬家、不改名、不自动删除源文件。

## 建议技术栈

| 层次 | 建议 | 理由与边界 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、成熟组件库 | 响应式统一界面，构建产物随应用镜像发布 |
| 后端 | Go，采用标准 HTTP 或 Gin 等轻量路由方案 | 核心服务与任务协调保持简单，媒体重处理交给独立执行进程 |
| 数据库 | 本机持久卷上的 SQLite | 首版无需部署数据库服务；短事务、受控写并发，硬件与库规模确定后进行验证 |
| 后台任务 | SQLite 持久队列与受管理的执行器 | 支持重试、取消、断点恢复、执行租约与资源限制，不以启动 Redis 为前提 |
| 视频处理 | FFmpeg、ffprobe、浏览器播放器 | 优先直播放，按浏览器与媒体能力决定是否转封装或转码 |
| 图片处理 | 缩略图生成库，特殊格式解码按需引入 | 首版优先常见 JPEG、PNG、WebP，RAW、HEIC 与动态/色彩兼容另设验收样本 |
| 漫画阅读 | 图片目录/CBZ 索引与独立漫画阅读器 | 首版支持自然页序、系列/章节、阅读方向和按页进度，CBR/PDF 后续评估 |
| 小说阅读 | TXT 阅读器、EPUB 阅读组件 | 首版为本地 TXT 与无 DRM EPUB，PDF 等其他图书格式后续评估 |
| 发布 | 单应用镜像与 Docker Compose | 目标支持 linux/amd64、linux/arm64；需验证各架构依赖后才能声明支持 |

## 内容与文件模型

- `Library`：媒体库类型、根目录、扫描策略与库级访问控制。
- `ContentItem`：内容标题、描述、封面、来源、标签、收藏和可见状态。
- `MediaFile`：独立文件标识、所属媒体库、相对路径、大小、修改时间、可选哈希、探测版本和最后发现时间。
- `VideoMetadata`、`ImageMetadata`、`ComicMetadata`、`NovelMetadata`：各类型专用字段，避免大量无关空字段。
- `ComicSeries`、`ComicChapter`、`ComicPage`：系列、卷/章节和有序页面，关联源目录或归档文件。
- `UserProgress`：按用户保存进度；视频为时间位置，漫画为章节与页标识，TXT 为可恢复文本位置，EPUB 为文档定位信息，图片为相册内位置。
- `ProcessingJob`：任务类型、对象版本、幂等键、状态、重试次数、租约与错误摘要。

作品与文件分开建模，支持一部作品多个文件。目录路径不能作为内容主键；完整哈希可用于确认重复文件，抽样哈希只能筛选候选。跨文件系统 inode 不作为通用稳定身份。

## 四类内容的首版处理

### 视频

扫描与探测元数据、提取海报、列表筛选、断点续播。先按浏览器能力直接播放兼容的内容；支持鉴权后的 HTTP Range。格式不兼容时给出清晰原因。超大视频的 64 位偏移、有界内存传输、快速拖动、任务取消和缓存空间限制纳入首版，见 [large-video.md](large-video.md)。不因文件体积大就默认全片转码；转封装与 HLS 转码根据真实格式/网络需求排期，在真实 NAS 上验证后开放硬件加速；不能将一个封装扩展名等同于浏览器可播放。

### 图片

按文件夹和日期浏览，响应式网格、缩略图、大图查看与标签收藏。元数据和缩略图后台生成，长列表分页/虚拟化；默认不修改源图。EXIF 位置信息是否展示遵守用户设置。首版不依赖人脸识别与 AI 模型。

### 漫画

提供独立漫画书架，以系列、卷/章节、页面组织。首版接入图片目录与 CBZ，文件名使用自然排序并提供导入预览；支持单页、双页、连续滚动和左右阅读方向，保存章节与页标识。图片解码/缩略图与相册复用底层能力，目录、进度和阅读界面独立。压缩包处理限制解压大小、文件数、嵌套层级与路径范围，避免导入时任意覆盖文件；CBR/PDF 作为后续格式扩展，单独验证解码与发布依赖。

### 小说

支持 TXT 编码识别及必要的手动纠正、章节切分预览、无 DRM EPUB 目录与阅读。提供字号、行距、主题和跨设备阅读进度。章节识别失败时允许按全文阅读，避免导入失败；不执行书籍中的脚本或任意活动内容。

## 扫描与任务流程

1. 首次向导校验媒体目录可读，后台扫描；列表边扫描边可用。
2. 文件新增或变化后建立或更新索引，再提交探测、封面或解析任务。
3. 本地监听仅用于加速，定期目录对账作为正确性保障；网络挂载不能只靠文件事件。
4. 挂载不可达或整次扫描失败时不将全库判为已删除；源文件消失先标记缺失，成功复查后再处理索引状态。
5. 任务按内容版本与处理配置生成幂等键；错误重试有上限，可取消，重启后可恢复待处理任务。
6. 媒体处理设置并发、缓存容量和超时上限；API 请求不执行长时间媒体处理。
7. 对软链接和最终规范化路径校验根目录边界，下载与播放请求都进行库权限检查。

## 易用性要求

- 首次使用向导只要求创建管理员、选择媒体目录和确认扫描。
- 导航以“视频、图片、漫画、小说、收藏、最近访问”为中心，管理配置集中在设置页。
- 任务面板显示待处理、处理中、成功与失败，以及可读的中文错误和重试入口。
- 默认配置可以使用；转码、远程访问、AI 等高级功能按需打开。
- 首版以响应式 Web 覆盖电脑、平板与手机，暂缓原生客户端。
- 空目录、权限不足、格式不支持、空间不足和扫描未结束均提供明确状态与处理建议。
- 首页优先“继续观看/阅读”和最近添加；视频使用海报墙、图片使用时间线、漫画使用系列书架、小说使用文字信息清晰的书架。
- 明暗主题、统一色彩/间距/图标、响应式布局和阅读沉浸模式均纳入产品要求，详见 [visual-design.md](visual-design.md)。

## 部署与数据组织

- `/data`：应用本机持久目录，包含数据库、配置和可重建缓存；数据库不放 SMB/NFS 网络共享。
- `/media/video`、`/media/image`、`/media/comic`、`/media/novel`：来自 NAS 的只读媒体挂载，不要求改变现有目录结构。
- 容器映射一个 Web 端口；仅在需要反向代理和外网 HTTPS 时增加对应组件。
- 进程按非 root 用户运行，文档解释 UID/GID 与目录权限；持久目录可写、源媒体默认只读。
- 首次部署提供图形化容器管理器与 Compose 两条文档路径。宿主机路径配置仍需用户完成，网页不声称能够绕过容器挂载任意选择宿主目录。
- 每个配置项、环境变量和示例参数都需要中文解释；提供默认值与必要校验。
- 版本固定到可追踪标签，升级前备份；数据库迁移兼容性必须纳入恢复演练，不能承诺仅回滚镜像即可恢复旧数据库。
- 备份采用一致性快照或停机备份，不直接复制运行中 SQLite 主文件来代替完整备份；原始媒体仍需单独备份。

## 分阶段建议

| 阶段 | 范围 | 验收重点 |
| --- | --- | --- |
| 第一阶段：统一基础 | 视觉设计、单容器发布、首次向导、媒体库、扫描、任务、标签收藏、四类内容基础浏览 | 新环境启动后可通过向导建库，重启数据保留，挂载断开不误删 |
| 第二阶段：完整使用闭环 | 兼容视频直播放与进度、图片查看、漫画阅读、TXT/EPUB 阅读与进度、基础搜索 | 四类内容均可在桌面与手机浏览器完成消费并恢复进度 |
| 第三阶段：兼容与维护 | 受控转封装/转码、硬件加速验证、备份恢复、升级流程、权限细化 | 在确认硬件与格式样本上通过兼容测试，完成一次恢复演练 |
| 后续按需 | AI 分类、人脸识别、OCR、全文中文检索、下载器集成、原生客户端 | 独立评估资源、依赖、隐私与维护成本 |

可公开交付的首版应覆盖前两阶段，并具备基础备份恢复；若用户需要广泛视频格式兼容，应把转码列入首版条件。

超大视频是独立首版验收场景，覆盖起播、拖动、长时间播放、重连与资源边界。具体大小和性能阈值待样本、硬件与网络确认；不能以“支持普通视频”替代超大文件测试。

## 替代方案与取舍

- 成熟软件组合：使用 Jellyfin、Immich、Kavita 等各自完整的服务，适合尽快使用成熟专用功能，但需要多套部署、账户/权限与数据维护，统一入口不等同于统一后台。
- 推荐方案：统一自建管理系统，复用媒体处理和阅读组件，四类内容通过一套界面使用。针对性强、最终操作与部署更一致，但必须接受首版格式与功能边界。
- 深度整合现有服务：只通过官方公开 API 做有限对接，独立保留服务数据；需要另做 API 稳定性、授权、账号映射和许可评估，不能直接写第三方数据库。

## 待确认事项

最先确认 NAS 型号与配置，以确定容器支持、镜像架构与转码可行性。随后确认内容规模、多用户与外网需求。最终框架和数据库选择仍以用户偏好与样本验证为准。
