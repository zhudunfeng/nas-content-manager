# Account lifecycle contract

## 1. Scope / Trigger

Applies to administrator credentials, session storage/authentication, and account maintenance. S02.1 introduces additive schema 5 and login snapshot checks; S02.2 implements the online account APIs and the local account-security settings panel. S02.3 adds the explicitly offline reset command. All three slices have completed local independent acceptance; actual Linux/NAS locks, terminals, permissions and deployment acceptance remain pending. Slice evidence and independent reviews live under the S02 task; Windows checks do not constitute target NAS acceptance.

## 2. Signatures

- `migrateAccountSchema(ctx context.Context, tx *sql.Tx) error` adds schema 5 within the normal migration transaction.
- `saveAccountSession(ctx context.Context, db *sql.DB, account accountSnapshot, session storedAccountSession) error` inserts a session only if user ID, password hash and credential revision still match.
- `readAccountSession(ctx context.Context, reader accountRowReader, tokenDigest string, timestamp time.Time) (authenticatedAccountSession, error)` supports both `*sql.DB` and `*sql.Tx`; sensitive transactions must reuse their transaction reader rather than request another connection.
- `deleteExpiredAccountSessions(ctx context.Context, db *sql.DB, timestamp time.Time) error` performs conservative historical cleanup. Authentication performs the authoritative exact expiry check.
- `(*App).createSession(w http.ResponseWriter, r *http.Request, account accountSnapshot) bool` writes a Cookie only after the conditional insert succeeds.
- Schema 5 adds `users.auth_revision INTEGER NOT NULL DEFAULT 0 CHECK(auth_revision>=0)` and session fields `session_id`, `created_at`, `client_browser`, `client_os`, `auth_revision`. Historical schema constants remain unchanged.
- `POST /api/account/password` accepts exactly `{currentPassword:string,newPassword:string}` and returns `{requiresLogin:true}` after changing credentials and deleting all account sessions.
- `GET /api/account/sessions?limit=20&cursor=v1.<lowerhex32>` returns `{currentSession:AccountSession,items:AccountSession[],nextCursor:string|null}`. `AccountSession` contains only `id,current,clientBrowser,clientOS,createdAt:string|null,expiresAt:string`.
- `DELETE /api/account/sessions/{sessionId}` returns `{requiresLogin:boolean}`; `POST /api/account/sessions/revoke-others` accepts exactly `{currentPassword:string}` and returns `{requiresLogin:false,revokedCount:number}`.
- `changeAccountPassword(ctx context.Context, db *sql.DB, actor accountMutationActor, newPasswordHash string) error`, `revokeAccountSession(..., targetSessionID string) (bool,error)` and `revokeOtherAccountSessions(...) (int64,error)` run bounded short transactions using the actual Cookie snapshot.
- `accountReauthLimiter.reserve(userID int64, sessionID string, timestamp time.Time) time.Duration` atomically reserves the independent account and actual-session budgets before bcrypt.
- `nas account reset-password --data-dir <existing-local-directory> [--password-stdin]` resets the existing administrator while the service is stopped. Only the exact `nas account reset-password --help` form displays help.
- `RunAccountMaintenance(ctx context.Context, args []string, input *os.File, output io.Writer, diagnostic io.Writer) int` is dispatched before normal configuration/runtime initialization whenever the CLI has arguments.
- `openOfflineAccountDatabase(ctx context.Context, path string) (*sql.DB, offlineAccountSnapshot, error)` opens only an existing explicitly supported account schema; `resetOfflineAccountPassword(ctx context.Context, db *sql.DB, expected offlineAccountSnapshot, newHash string) error` performs the independent CAS transaction without fabricating an online actor.
- `validOfflinePasswordHash(hash string) bool` checks the explicitly supported stored bcrypt shape and cost, without claiming to verify an unknown old password.
- `discardOversizedAccountBody(w http.ResponseWriter, r *http.Request)` bounds the account decoder's known-oversized rejection path before sending 413; this is separate from the shared small-body cleanup.

## 3. Contracts

- Preserve existing users/password hashes, session token hashes/expiry, media, user state, jobs, downloads and collection rows. Existing unexpired cookies continue working after migration; no global logout is used to avoid assigning metadata.
- `session_id` is a separately generated 128-bit lowercase hexadecimal public identifier. The 256-bit bearer token is generated independently; only its SHA-256 digest is stored. Never derive a public ID from the token/digest or expose either private value.
- Migration assigns an independent random ID to every historical session. Historical `created_at` remains SQL NULL and historical client categories are `unknown`; do not infer creation times or devices. Session IDs are unique/nonempty after backfill; insertion and update triggers reject migration-only empty values.
- Browser categories are `unknown/chrome/edge/firefox/safari/opera/other`; OS categories are `unknown/windows/macos/linux/android/ios/other`. Empty or over-1024-byte UA maps to `unknown`. Categories are display hints, not trusted device identities. Do not store raw UA, IP or versions.
- Setup/login carry the actual user/hash/revision snapshot through bcrypt work. One `INSERT ... SELECT ... WHERE id=? AND password_hash=? AND auth_revision=?` checks it again. A stale result cannot create a new valid session. Do not hold a SQLite transaction over bcrypt.
- Authentication requires a matching session/user revision and parsed `expires_at.After(timestamp)`. RFC3339Nano contains variable fractional precision, so textual comparison cannot determine exact expiry. An invalid stored time fails authentication.
- Cleanup uses a conservative UTC date cutoff at least 24 hours earlier; it may retain recently expired rows, which remain unusable. Do not replace exact authentication with cleanup or compare same-second timestamp strings.
- Existing login preserves the submitted password, including legacy weak/Chinese passwords, with its existing 72-byte bound. New-password policy remains the shared explicit ASCII policy. Logs must contain only action results and safe IDs.
- Account JSON requires `application/json`, a single object, exact case-sensitive camelCase keys and string values within the shared 64 KiB cap. Reject missing/unknown keys, aliases, decoded duplicate keys (including Unicode escapes), null, nested values and trailing content. Parser errors are fixed Chinese messages, never raw decoder details containing a secret.
- For a JSON request with known `ContentLength>64<<10`, set `Connection: close` and perform the account-local rejection cleanup before 413. If there is any Expect value, no body, or no supported read-deadline capability, consume nothing. Otherwise use a local 250 ms read deadline and a real `http.MaxBytesReader` to consume at most 65,537 actual bytes without parsing or retaining them. Restore the deadline after success or the expected `MaxBytesError`; after premature EOF, timeout or another failure retain an expired deadline so native close cannot wait again. Unknown-length requests keep the existing limited decoder. Do not increase the accepted size, retry requests, synthesize limit hits, or alter the shared middleware's large/unknown/Expect skip rules. Go's native limit-hit close may add its own fixed 500 ms half-close wait; the local budget is neither a whole-connection deadline nor a guarantee of delivery under arbitrary network conditions.
- A current password has only the existing 72 UTF-8-byte bound; do not trim it or apply new complexity, character or nonempty rules. A new password uses the shared 10–72 ASCII four-class policy. Wrong current password is 400, so it cannot trigger the frontend's global session-expired behavior.
- Password comparison and new bcrypt generation occur outside SQLite transactions. Inside a sensitive transaction, first compare expected user ID/hash/revision (changed means 409), then validate the actual session through the same `*sql.Tx` (revoked/expired with unchanged account means 401). Check context cancellation and real expiry again after writes and immediately before commit; roll back every failed transaction. Self-revocation and password change use the transaction's already validated expiry after deleting their own row. Refuse credential revision overflow.
- Clear the Cookie and emit success logs only after commit. An already admitted media transfer may finish; subsequent requests must fail with revoked credentials. An uncertain network response never authorizes automatic replay of a sensitive mutation.
- `limit` defaults to 20 and accepts 1..100; cursor is absent or exactly `v1.` plus 32 lowercase hex digits. Reject unknown, duplicate or empty-valued query parameters. Query raw rows by public ID ascending with `LIMIT limit+1`, process only the first `limit` rows and use the extra row only for lookahead. At one shared as-of time, parse exact expiry and filter current, expired, malformed-time and stale-revision rows. Do not fetch more rows to fill a page. `nextCursor` is the last consumed raw ID, not the last displayed item; empty `items` with a non-null cursor is valid. The actual current session is separately pinned on every batch. This is neither login-time ordering nor a global multi-request snapshot.
- Single revocation is idempotent and scoped to the actual account; only revoking its real current ID clears the Cookie. Revoke-others retains the current record and returns the precise transaction `RowsAffected`, including expired and stale-revision records. Do not label this value active devices.
- Password change and revoke-others share process-local fixed-window reauthentication limits: 12 attempts per account and 6 per `(userID,sessionID)` in five minutes. Successful and failed bcrypt attempts both reserve both counters atomically. A new login, a new session or success does not clear the account budget. Remove expired counters; cap the combined key count at 2048 and conservatively refuse new keys when full rather than evicting live budgets. 429 includes ceil remaining seconds clamped to 1..300 in `Retry-After`. This does not provide persistence across restart.

### Explicitly offline maintenance

- No arguments starts the original service; any argument selects strict maintenance parsing and must never fall back to service startup. Accept only space-separated `--data-dir <value>` and one optional `--password-stdin`; reject `--data-dir=<value>`, duplicates, missing values, unknown commands/positionals and password arguments. Do not echo rejected values. Exact help performs no configuration, filesystem, database or network initialization. Environment variables never supply a maintenance password.
- Require an existing canonical local directory and ordinary non-link `library.db`; UNC is not supported. Reuse the existing canonical `.nas-instance.lock` platform primitive directly, without the startup helper that creates directories. Recheck file identity after locking and before writing. Hold the same lease until after SQLite closes; never unlink a held lock, break a live owner or kill another instance. The lease coordinates cooperating application instances, not arbitrary same-user filesystem tampering.
- Use a properly escaped `file:` URI with fixed `mode=rw`, one connection, connection-local foreign keys/busy timeout/trusted-schema settings. Never use `openDatabase`, `LoadConfig` or `Run`, change journal mode, migrate, create an administrator, recover jobs/external actions, scan media or clean caches. Opening SQLite may recover its own required journal state; the guarantee is no unrelated application business mutation, not arbitrary corrupt-file byte immutability.
- Explicitly support only the set `{5,6}` through `supportsOfflineAccountSchema(version int64) bool`, independently of the normal startup head-version constant. Schema 6 only adds the backup storage described in [Backup storage contract](./backup-storage-contract.md); maintenance neither reads policy nor prepares/reconciles its root. Inspect actual account tables, field types/nullability/primary and foreign keys, the two known public-session-ID triggers, and dangerous extra trigger/cascade references. Read at most two administrators and require exactly ID 1, valid SQLite types, a bcrypt hash and a nonnegative non-overflowed revision. This narrow preflight is not a full large-library integrity scan. Every future schema migration must separately review and test the maintenance support set rather than automatically widening it through a shared constant.
- A stored bcrypt hash must be exactly 60 bytes with `$2a$`, `$2b$` or `$2y$`, or the compatible historical 59-byte `$2$` form. The cost is exactly two ASCII digits in 4..31, followed by the fixed delimiter and exactly 53 characters from `./ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789`. Check this before `bcrypt.Cost`, both at preflight and transactional reread. Reject extra suffixes, signed costs, unknown minor versions and invalid salt/digest characters. This is format/cost validation, not old-password verification or a claim about canonical padding bits.
- Input and bcrypt occur outside a write transaction. Preflight retains separate actual `user_version` and `schema_version`, administrator ID/hash/revision; the short write transaction requires the user version to remain supported and equal the preflight value as well as matching the schema cookie/account snapshot. Both 5→6 and 6→5 drift fail even if the schema cookie is unchanged. Conditionally change hash and increment revision, delete all that administrator's sessions, check cancellation immediately before commit and require the CAS to affect one row. Preserve nonempty backup-domain rows, pending sentinels and every unrelated business domain. Roll back any failure. An unconfirmed commit or failed rollback is an unknown outcome: require verification, never claim unchanged state or retry automatically. After confirmed commit, later cancellation/cleanup/output failure cannot turn the result into a rollback claim.
- Default input must be a real terminal and confirms the password twice without echo. Explicit `--password-stdin` requires redirected input and refuses a terminal. Read at most 75 bytes including the overflow sentinel; a shorter input still needs EOF. Strip only one final LF or CRLF, reject remaining line breaks, and apply the same untrimmed 10–72-byte ASCII policy. Never accept a valid prefix of oversized input.
- Pin official `golang.org/x/term v0.48.0` with the repository's compatible Go/x/sys versions. The controlling goroutine synchronously calls `MakeRaw` before starting the official `Terminal.ReadPassword` reader, owns the sole `Restore`, and restores before hashing/writing. The reader never changes OS modes. Count at most 1024 raw non-line-ending bytes per prompt; invalid bytes or overflow remain invalid after editing. Handle CRLF across prompt boundaries. Confirmation mismatch, Ctrl+C/Ctrl+D, context/system cancellation, prompt-write failure or restore failure prevents mutation. A cancellation-unblocked main may exit with a blocked read goroutine only because this is a dedicated maintenance process; do not reuse it as a long-lived input service.
- Exit 0 means confirmed commit and successful cleanup/result output, or successful help; 2 means usage error; 1 means precondition/input/storage/restore/cleanup/output failure or unknown outcome; 130 is reserved for pure precommit cancellation with successful cleanup. Fixed Chinese diagnostics/logs expose no input, hash, token/digest, raw SQLite error or unknown argument. Preserve joined cleanup errors instead of normalizing every error containing cancellation to 130.

## 4. Validation & Error Matrix

| Condition | Result |
| --- | --- |
| Database version above the current runtime head (6) | Refuse startup; no guessed downgrade |
| Migration/backfill/constraint failure | Roll back the schema-5 transaction; report failure |
| Password hash or revision changes after bcrypt verification | Conditional insert affects zero rows; login returns 409 and no new Cookie |
| Missing session, mismatched revision, malformed expiry, or expiry equal to/before now | Authentication fails; protected endpoint returns 401 |
| Unique/format/empty public ID violation | SQLite rejects the write |
| Unavailable historical client metadata | NULL creation time / `unknown` categories, without fabricated values |
| Cleanup failure after a valid session insert | Keep the valid login; log a sanitized Chinese warning and retry cleanup on a later login |
| Wrong current password / invalid new password / strict JSON or query rejection | 400, fixed Chinese explanation, unchanged account; wrong password preserves the valid login |
| Missing or incompatible JSON content type / oversized body | 415 / 413 |
| Known oversized account JSON with close-connection client | Bounded local rejection path then 413; any transport error fails verification rather than counting as 413 |
| Foreign-origin mutation | Existing global 403; account endpoints do not bypass same-origin protection |
| Unchanged account but current session revoked/expired before sensitive write or commit | 401 and transaction rollback |
| Concurrent credential change or revision overflow | 409 and rollback; no new Cookie |
| Reauthentication account/session budget exhausted or bounded map full | 429 with `Retry-After`; no bcrypt or mutation |
| Unknown or already revoked other public session ID | 200 with `requiresLogin:false`, without exposing record existence |
| Successful password change / current revocation | 200 requiring login, clear Cookie only after commit |
| Storage or cancellation failure | Safe 503, no raw storage error or success claim |
| Offline invalid/unknown/duplicate argument or unsupported equals-form flag | Exit 2, fixed usage only; no service fallback |
| Offline exact help | Exit 0, fixed help, no resource initialization |
| Offline live owner/alias, absent or linked DB, unsupported schema/structure, missing administrator, permission failure or overflow | Exit 1; no account mutation, forced unlock or application startup |
| Offline input invalid/mismatched, nonterminal without explicit stdin, or terminal with explicit stdin | Exit 1; no account write |
| Offline pure precommit cancellation / terminal restore failure | Exit 130 / exit 1; no account write |
| Offline commit/rollback unknown, or confirmed commit followed by cleanup/output failure | Exit 1 with truthful outcome; never claim rollback or retry automatically |
| Offline successful reset | Exit 0; new hash, revision +1, all old sessions deleted; normal fresh login required |

## 5. Good / Base / Bad Cases

- Good: a real schema-4 database with an existing bcrypt hash and Cookie upgrades to 5; the same Cookie authenticates, and each old session has a unique independently generated ID.
- Base: a newly created session has seven-day expiry, actual creation time, safe category hints and the current revision; restarting preserves it.
- Boundary: for `12:00:00Z`, `12:00:00.1Z`, and nanosecond variants, expiry is decided by `time.Time` regardless of string order. Equality is expired.
- Bad: bcrypt validates a snapshot, then another operation changes only the hash, only the revision, or both. All old snapshots must fail to create sessions.
- Good: two real browser sessions log in; revoking the other invalidates only it, revoke-others keeps the current Cookie, and changing the password invalidates every old Cookie and old password.
- Boundary: the first raw batch contains only expired records while a lookahead row exists; return an empty array with the consumed cursor, and let the user explicitly continue.
- Bad: switch sessions to bypass a per-session budget, or submit `CurrentPassword`, a duplicate escaped key or a second JSON object; none may reach bcrypt or account mutation.
- Good: stop the service normally, run the exact reset command on its existing local data directory, confirm twice, restart, and observe that every old Cookie/password fails while the new password works.
- Bad: pass an unknown command with an otherwise valid server environment, reset an active directory through an alias, or send a valid password prefix without EOF; none may start the server or change credentials.
- Bad: append bytes to an otherwise valid bcrypt hash or replace its two-digit cost with `+4`; a permissive cost parser is not sufficient to authorize a reset.
- Boundary: a 1 TiB declared account body that stalls after one byte reaches the local read deadline; Expect receives no 100 Continue, and a body exactly 64 KiB still enters normal JSON validation.

## 7. Wrong vs Correct

Wrong: validate bcrypt, then insert a session using only `user_id`; a concurrent password change can be followed by a fresh old-password session. Correct: retain the exact verified hash/revision snapshot and condition the insert on all three values, checking `RowsAffected()==1` before setting a Cookie.

Wrong: `WHERE expires_at > nowString` on RFC3339Nano values. Correct: load and parse the stored value, then require `expiry.After(now)`, using the transaction reader when already inside a sensitive short transaction.

Wrong: build the latest schema and only lower its `user_version` for a migration test. Correct: create the frozen historical schema first, copy only its original fields and assert values survive the full incremental migration.

Wrong: return 401 for a mistyped current password, or retry a failed password POST automatically. Correct: return 400 while the actual session is valid; on an uncertain result offer read-only confirmation or a fresh login.

Wrong: paginate by the last displayed valid item, repeatedly refill empty filtered batches, or sort random public IDs as recent-login order. Correct: bound raw work, advance by the last consumed raw row and separately pin the actual current session.

Wrong: reuse normal `openDatabase` for reset, concatenate a plain filename with `?mode=rw`, race top-level `term.ReadPassword` against `Restore`, or use `errors.Is(err, context.Canceled)` to discard joined cleanup failures. Correct: existing-only escaped URI, explicit supported structure, shared data lease, synchronous raw-mode ownership, unique restore and truthful transaction/cleanup outcome.

Wrong: treat `bcrypt.Cost(hash)==nil` as complete stored-format validation. Correct: validate exact prefix, length, two ASCII cost digits and payload alphabet first, then check the cost range.

Wrong: accept a connection reset as an oversized-body rejection or generalize the small-body defer to unbounded input. Correct: assert the real HTTP status and use the account-local byte/time-limited path while retaining native close semantics and the shared skip rules.
